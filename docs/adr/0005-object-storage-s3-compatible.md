# ADR-0005: ใช้ Object Storage แบบ S3-compatible เข้าถึงผ่าน Signed URL (ผู้ให้บริการยังไม่ตัดสินใจ)

**สถานะ:** Accepted (บางส่วน — สถาปัตยกรรมการเข้าถึงตัดสินแล้ว, ผู้ให้บริการยังรอ Owner ตัดสินใจ)
**วันที่:** 2026-09-14
**ผู้ตัดสินใจ:** Principal Software Architect / QA-Security Engineer
**อ้างอิงคู่กับ:** `requirements.md` M8, `user-flows.md` Flow 4 (เอกสาร), `data-policy.md` ข้อ 2/8

## บริบท (Context)

ระบบต้องจัดเก็บไฟล์ประเภทต่าง ๆ (เอกสารแนบทะเบียน, ใบประกาศนียบัตร PDF, ไฟล์ข้อสอบ) ที่ส่วนใหญ่จัดเป็นข้อมูล
Restricted (`data-policy.md` ข้อ 2) ต้องควบคุมสิทธิ์การเข้าถึงระดับไฟล์ให้สอดคล้องกับ RBAC ของข้อมูลต้นทาง
และต้องแยก environment (dev/staging/prod) อย่างชัดเจน (`data-policy.md` ข้อ 8)

## การตัดสินใจ (Decision)

1. ใช้บริการ Object Storage ที่รองรับ **S3-compatible API** (ผู้ให้บริการเฉพาะยังไม่ตัดสินใจ — ดูเกณฑ์เลือกด้านล่าง)
2. **เข้าถึงไฟล์ผ่าน signed URL ที่มีอายุจำกัด (short-lived) เท่านั้น** สร้างจาก Web/App layer หลังตรวจสิทธิ์
   สำเร็จ — ไม่มี public URL ที่เดา/เข้าถึงได้โดยไม่ตรวจสิทธิ์ (`user-flows.md` F4.2)
3. แยก bucket หรืออย่างน้อยแยก prefix ต่อ environment พร้อมสิทธิ์เข้าถึงที่แยกกัน (`data-policy.md` ข้อ 8)

## เกณฑ์การเลือกผู้ให้บริการ (สำหรับตัดสินใจในเฟสถัดไป)

- รองรับ S3 API มาตรฐาน (compatibility กับ AWS SDK)
- ตั้งค่า bucket policy/IAM แยกสิทธิ์ตาม environment ได้
- มี region ที่เหมาะสมด้านความหน่วงสำหรับผู้ใช้ในประเทศไทย
- รองรับ lifecycle policy (ย้ายไฟล์เก่าไป storage class ราคาถูกกว่า หรือลบตามนโยบายเก็บรักษาข้อมูลเมื่อ
  `data-policy.md` ข้อ 9 สมบูรณ์)
- ต้นทุนเหมาะสมกับขนาดการใช้งานที่คาดการณ์ (ยังไม่มีตัวเลขที่แน่นอน — dependency ที่ต้องประเมินร่วมกับ Owner)

## ทางเลือกที่พิจารณา (Alternatives Considered)

1. **เก็บไฟล์ในเครื่อง server เอง (local filesystem)** — ปฏิเสธ เพราะไม่รองรับ horizontal scaling ของ Web/App
   layer (หลาย instance ต้องเห็นไฟล์เดียวกัน) และกู้คืนยากกว่ากรณี server ล่ม
2. **เก็บไฟล์เป็น BLOB ใน PostgreSQL** — ปฏิเสธ เพราะไฟล์ PDF/เอกสารแนบมีขนาดใหญ่กว่าข้อมูลเชิงสัมพันธ์ทั่วไปมาก
   จะทำให้ฐานข้อมูลหลักโตเร็วเกินจำเป็นและกระทบ performance ของ query อื่น
3. **ผูกกับผู้ให้บริการเฉพาะเจ้าใดเจ้าหนึ่งตั้งแต่ตอนนี้** — ปฏิเสธ เพราะยังไม่มีข้อมูลเพียงพอเปรียบเทียบต้นทุน/
   ข้อกำหนดขององค์กร จึงตัดสินใจเฉพาะ "รูปแบบการเข้าถึง" (S3-compatible + signed URL) ก่อน เพื่อไม่ผูกกับ
   SDK/API เฉพาะเจ้าใดเจ้าหนึ่งในโค้ดแอปพลิเคชัน

## ผลกระทบ (Consequences)

**ด้านบวก:**
- Portable ข้ามผู้ให้บริการ (S3-compatible API เป็นมาตรฐานกว้าง) — ตัดสินใจเรื่อง provider ทีหลังได้โดยกระทบ
  โค้ดน้อยที่สุด
- Signed URL ป้องกันการเข้าถึงไฟล์โดยไม่ผ่านการตรวจสิทธิ์ได้อย่างมีประสิทธิภาพ

**ด้านลบ / ข้อควรระวัง:**
- ต้องดูแลอายุของ signed URL ให้สั้นพอที่จะจำกัดความเสี่ยงหาก URL หลุดไปยังบุคคลอื่น แต่ยาวพอให้ดาวน์โหลดเสร็จ
  ก่อนหมดอายุ — ต้องทดสอบค่าที่เหมาะสมจริงในเฟส implementation
- ยังไม่มี provider ที่แน่นอน — เป็น dependency ที่ค้างอยู่ ต้องยืนยันก่อนเริ่มพัฒนา M8 จริง

## Failure Mode & Recovery ที่เกี่ยวข้อง

ดู `architecture.md` ข้อ 7 แถว "Object Storage" (2 รายการ) — สรุปสั้น: ไฟล์กำพร้าจากการอัปโหลดล้มเหลวกลางทาง
ต้องมี job ตรวจสอบเปรียบเทียบ storage กับ metadata เป็นระยะและลบ/แจ้งเตือน; หาก provider ล่มทั้งระบบ แอปต้อง
แสดงข้อความชัดเจนแก่ผู้ใช้แทน error ดิบ และทำงานต่อได้ทันทีเมื่อ provider กลับมาโดยไม่มี state ค้างฝั่งแอป
