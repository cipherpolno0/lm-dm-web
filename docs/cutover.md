# cutover.md — แผนปฏิบัติการ Cutover สู่ข้อมูลจริง (P9 Real-data Readiness)

**งาน:** Production Readiness Gate + Cutover Plan
**Phase:** P9 Real-data Readiness
**สถานะเอกสาร:** จัดทำ/ออกแบบเสร็จ — **ยังไม่เคยถูกซ้อม (rehearse) หรือใช้งานจริง**
**สถานะ Gate ปัจจุบัน (อ้างอิง `readiness-checklist.md`): 🔴 NO-GO** — ห้ามเริ่มขั้นตอนใดในเอกสาร
นี้กับข้อมูลจริงจนกว่า `readiness-checklist.md` หัวข้อ 0 จะแสดง **GO** (ทุก gate ที่จำเป็น = Approved)

> เอกสารนี้เป็น "แผนที่พร้อมใช้เมื่อได้รับอนุญาต" ตามที่บรีฟงานนี้ระบุให้ส่งมอบคู่กับ
> `readiness-checklist.md` — การมีเอกสารนี้อยู่ **ไม่ได้แปลว่าอนุญาตให้ใช้ข้อมูลจริงแล้ว**

---

## 1. ก่อนเริ่ม: เงื่อนไขบังคับ (Preconditions)

ต้องผ่านครบทุกข้อก่อนกำหนดวัน cutover จริง:

1. `readiness-checklist.md` แสดงสถานะ **GO** — โดยเฉพาะ G1/G5/G7 (PDPA + retention/erasure +
   Owner sign-off) ต้องเป็น Approved ไม่ใช่ Blocked
2. Owner เซ็นอนุมัติเป็นลายลักษณ์อักษรระบุ **ขอบเขตข้อมูลจริงที่อนุญาตนำเข้าครั้งนี้โดยเฉพาะ**
   (เช่น จำนวนองค์กร/บุคคล ช่วงเวลา แหล่งที่มา) — ไม่ใช่การอนุมัติแบบเหมาว่าใช้ข้อมูลจริงได้ตลอดไป
3. ไฟล์ข้อมูลจริงที่จะนำเข้าผ่านการตรวจสอบตาม `real-data-mapping.md` แล้ว (คอลัมน์/รูปแบบตรงตาม
   ที่ import pipeline คาดหวัง)
4. ทำ **dry-run rehearsal** ตามขั้นตอน §2-8 ของเอกสารนี้กับสำเนาข้อมูลจริงชุดแรก (หรือชุดตัวอย่าง
   ที่ Owner อนุมัติ) อย่างน้อย 1 ครั้งในสภาพแวดล้อมแยก (`scripts/dry-run-db.sh`, วิธีเดียวกับ
   Task 24 — ดู `migration-dry-run-report.md`) **ก่อน**ใช้กับฐานข้อมูล production จริง
5. Backup ฐานข้อมูล production ปัจจุบัน (ก่อน cutover) ผ่านการทดสอบ restore สำเร็จแล้วในสัปดาห์
   เดียวกับ cutover (ไม่ใช้ผลทดสอบเก่าเกิน 7 วัน — ข้อมูลอาจเปลี่ยนแปลงไปมากตั้งแต่นั้น)

## 2. บทบาทและความรับผิดชอบระหว่าง Cutover

| บทบาท | หน้าที่ | หมายเหตุ |
|---|---|---|
| **Release Manager** | สั่งเริ่ม/หยุด/ตัดสินใจ Go-No-Go ที่ checkpoint ทุกจุด, ประกาศ freeze window | ต้องเป็นคนเดียวที่ตัดสินใจสุดท้ายในแต่ละ checkpoint เพื่อไม่ให้เกิดการตัดสินใจซ้อนทับกัน |
| **DB Operator** | รันคำสั่ง backup/import/restore จริงทั้งหมดตาม §5-6 | ต้องมี admin credential แยกจาก credential ของแอป (ดู `ops-runbook.md` §4 — least-privilege) |
| **Security Reviewer** | ยืนยันว่าไม่มีการเปลี่ยนแปลงโค้ด/สิทธิ์ใดๆ ระหว่าง freeze window (ดู §3) | ตรวจ audit log หลัง cutover ว่าไม่มี grant/revoke สิทธิ์ที่ไม่คาดคิดเกิดขึ้นระหว่างหน้าต่างเวลานี้ |
| **On-call / Monitoring** | เฝ้าดู `/api/health`, `/api/admin/system/metrics`, error log ระหว่างและหลัง cutover (ดู §9) | **ไม่มีระบบ alerting อัตโนมัติ** (ดู `readiness-checklist.md` หมวด Monitoring) — ต้อง poll ด้วยมือตามรอบที่กำหนด |
| **Owner** | อนุมัติเริ่ม cutover ก่อน Step 0, รับทราบผลหลัง cutover เสร็จ | คนเดียวกับที่เซ็น G7 ใน readiness-checklist.md |

ในทีมขนาดเล็ก บทบาทเดียวกันอาจทำหลายหน้าที่ได้ **ยกเว้น Release Manager กับ DB Operator ควร
เป็นคนละคนกัน** เพื่อให้มีการตรวจสอบไขว้ (four-eyes) ก่อนรันคำสั่งที่กระทบข้อมูลจริง

## 3. Freeze Window (นิยามใหม่ในงานนี้ — ไม่เคยถูกกำหนดมาก่อนในโครงการ)

**คำนิยาม**: ช่วงเวลาที่ **ห้าม deploy โค้ดใหม่, ห้ามรัน migration schema ใหม่, ห้าม grant/revoke
สิทธิ์ RBAC ใดๆ** (นอกเหนือจากขั้นตอน cutover เอง) เพื่อให้สถานะของระบบนิ่งพอที่จะเชื่อถือผล
reconciliation ของการนำเข้าข้อมูลได้ — เหตุผล: ถ้ามีการเปลี่ยน schema หรือสิทธิ์ระหว่างที่กำลัง
import ข้อมูลจริง จะแยกไม่ออกว่าความคลาดเคลื่อนที่เจอมาจากข้อมูลนำเข้าเองหรือจากการเปลี่ยนแปลง
ระบบพร้อมกัน

**ช่วงเวลา** (สัมพัทธ์กับเวลาเริ่ม cutover จริง = T0):

| ช่วง | สถานะ | อนุญาตให้ทำอะไรได้บ้าง |
|---|---|---|
| T-24h ถึง T0 | ประกาศ freeze แล้ว รอเริ่ม | อ่าน/ตรวจสอบเท่านั้น ห้าม deploy/migrate/grant สิทธิ์ |
| T0 ถึง T+ (จบ Step 8 §5) | Freeze เต็มรูปแบบ | เฉพาะขั้นตอนใน §5 ของเอกสารนี้เท่านั้น |
| T+ ถึง T+2h | Freeze ต่อเนื่องเพื่อสังเกตอาการ (post-cutover observation) | อ่าน/ตรวจสอบ + hotfix ฉุกเฉินเท่านั้น (ต้องได้รับอนุมัติจาก Release Manager เป็นกรณีไป) |
| หลัง T+2h (ถ้าไม่มีปัญหา) | ปลด freeze | กลับสู่การทำงานปกติ |

**ข้อยกเว้นฉุกเฉิน**: หากพบช่องโหว่ความปลอดภัยร้ายแรงระหว่าง freeze window, Security Reviewer
มีอำนาจขอ break-glass เพื่อ deploy patch ฉุกเฉิน — ต้องได้รับอนุมัติจาก Release Manager และบันทึก
เหตุผล/เวลา/ผู้อนุมัติไว้ในรายงานหลัง cutover (§11) เสมอ ไม่มีข้อยกเว้นแบบเงียบๆ

**การสื่อสาร**: ประกาศเริ่ม/จบ freeze window ให้ผู้ที่เกี่ยวข้องทั้งหมดทราบล่วงหน้าอย่างน้อย 24
ชั่วโมง (ตาม T-24h ข้างต้น) — ช่องทางการสื่อสารเฉพาะ (อีเมล/แชท) ไม่ได้ถูกกำหนดในเอกสารระดับ
โครงการที่มีอยู่ (`project-charter.md`/`requirements.md` ไม่ได้ระบุเครื่องมือสื่อสารทีม) — ทีมต้อง
ตกลงช่องทางจริงก่อนใช้เอกสารนี้ครั้งแรก (ดูหัวข้อ 12)

**สถานะการซ้อม**: ยังไม่เคยถูกซ้อมจริง — จัดเป็น Pending ใน `readiness-checklist.md` หมวด
Freeze Window จนกว่าจะมีการ rehearsal อย่างน้อย 1 ครั้ง (ดูเงื่อนไข §1 ข้อ 4)

## 4. Pre-Cutover Checklist

**T-7 วัน:**
- [ ] ยืนยันไฟล์ข้อมูลจริงพร้อม + ผ่านการตรวจสอบเบื้องต้นตาม `real-data-mapping.md`
- [ ] ยืนยัน Owner sign-off (G7) ยังไม่หมดอายุ/ไม่มีการเปลี่ยนแปลงขอบเขตที่อนุมัติ
- [ ] จองเวลา DB Operator + Release Manager + On-call ให้ตรงกับ T0 ที่วางแผนไว้

**T-1 วัน:**
- [ ] รัน dry-run rehearsal เต็มรูปแบบกับสำเนาข้อมูลจริง (§1 ข้อ 4) — บันทึกผลแยกเป็นรายงานใหม่
      (รูปแบบเดียวกับ `migration-dry-run-report.md`)

**T-2 ชั่วโมง:**

- [ ] ยืนยันไม่มี deploy ค้างอยู่ระหว่างดำเนินการ (CI/CD queue ว่าง)

## 5. ขั้นตอนปฏิบัติการ Cutover (Execution Sequence)

ใช้กลไกเดียวกับที่พิสูจน์แล้วใน Task 24 (`migration-dry-run-report.md`) และ Excel Import
Pipeline ที่มีอยู่จริง (`import-pipeline.md`, `src/app/actions/import.ts`) — คุณสมบัติสำคัญที่
ทำให้ขั้นตอนนี้ปลอดภัย: **preview ไม่เขียนข้อมูลใดๆ ลงตารางจริง** (validate-only) และ
**commit เป็น atomic ต่อกลุ่มแถวเสมอ** (ไม่มีข้อมูลค้างครึ่งๆ กลางๆ)

| Step | การกระทำ | ผู้รับผิดชอบ | เกณฑ์ผ่าน |
|---|---|---|---|
| 0 | เข้าสู่ freeze window เต็มรูปแบบ (T0) | Release Manager | ประกาศแล้ว + ทีมยืนยันรับทราบ |
| 1 | Backup ฐานข้อมูล production ปัจจุบัน (`npm run db:backup`) | DB Operator | ไฟล์ backup สร้างสำเร็จ ขนาด > 0 |
| 2 | ทดสอบ restore backup นี้เข้าฐานข้อมูลแยก (scratch) + เทียบ row count กับต้นทาง | DB Operator | ตัวเลขตรงกันทุกตาราง (วิธีเดียวกับ `readiness-checklist.md` §4.2) |
| 3 | อัปโหลดไฟล์ข้อมูลจริงเข้า Import Pipeline ในโหมด **Preview เท่านั้น** (ยังไม่ commit) | DB Operator | ได้ `reportJson` ที่มีสรุปจำนวนแถว valid/invalid ครบ |
| **Checkpoint #1** | **Go/No-Go**: ตรวจ reconciliation report เทียบกับ `real-data-mapping.md` ที่คาดไว้ | Release Manager | จำนวนแถว valid/invalid/สาเหตุ invalid ตรงกับที่คาดหมายในเชิงคุณภาพ (ไม่ใช่ทุกแถวต้อง valid 100% — แต่ invalid ต้องอธิบายได้ทุกแถว) ถ้าไม่ผ่าน → **ABORT** (ยังไม่มีข้อมูลใดถูกเขียนจริง เพราะ preview ไม่เขียน DB) |
| 4 | Commit การนำเข้า (เขียนข้อมูลจริงลงตาราง — atomic ต่อกลุ่มแถว) | DB Operator | Job แสดงสถานะเสร็จสิ้น |
| **Checkpoint #2** | **Go/No-Go**: ตรวจ commit reconciliation report (created/matched/failed) + สุ่มตรวจ audit_logs ว่ามีแถวใหม่ตรงจำนวนจริง | Release Manager + Security Reviewer | จำนวน created+matched+failed = จำนวนแถวทั้งหมด (ไม่มีแถวหายไปเงียบๆ) ถ้าไม่ผ่าน → เข้า §6-7 (Rollback) |
| 5 | รัน smoke test (`node scripts/smoke-test.mjs`) + ตรวจ login ตัวแทนแต่ละ role ที่มีสิทธิ์เกี่ยวข้องกับข้อมูลที่เพิ่งนำเข้า | On-call | ทุกรายการผ่าน |
| 6 | ตรวจ `/api/health` และ `/api/admin/system/metrics` | On-call | `status: ok`, row-count ที่ metrics รายงานสอดคล้องกับข้อมูลที่เพิ่งนำเข้า |
| 7 | ประกาศจบ freeze window (เข้าสู่ post-cutover observation ตาม §3) | Release Manager | — |
| 8 | บันทึกรายงานสรุปหลัง cutover (§11) | Release Manager | เอกสารรายงานเสร็จสมบูรณ์ |

## 6. Rollback — ระดับที่ 1: ต่อ Job การนำเข้า (พิสูจน์แล้วใน Task 24)

**เมื่อไหร่ใช้**: Checkpoint #2 ไม่ผ่าน แต่ปัญหาจำกัดอยู่ที่ job การนำเข้าเอง (ไม่กระทบข้อมูลอื่น
ในระบบ)

**กลไกที่มีอยู่แล้วและพิสูจน์จริง** (`migration-dry-run-report.md`, Task 24): การ commit แต่ละ
กลุ่มแถวอยู่ใน transaction เดียว — ถ้าแถวใดชนกับข้อมูลจริงที่มีอยู่แล้ว (เช่น referenceCode ซ้ำ
กับ appointment ที่ ACTIVE อยู่) transaction ของกลุ่มนั้น **rollback อัตโนมัติทั้งกลุ่ม ไม่มีข้อมูล
ค้างครึ่งๆ กลางๆ** — พิสูจน์จริงด้วยกรณี DBCONFLICT-01 และ UNIQUEFILE-01/02 ใน dry-run dataset
(19 แถว จงใจให้ 2 แถวชนกับข้อมูลจริงที่ commit ไปก่อนหน้าในไฟล์เดียวกัน → ทั้งคู่ rollback ถูกต้อง
ไม่กระทบแถวอื่นที่ commit สำเร็จแล้ว)

**ขั้นตอน**: ไม่ต้องทำอะไรเพิ่มเติมด้าน data-integrity (ระบบ rollback ให้เองแล้วที่ระดับ
transaction) — สิ่งที่ต้องทำคือ: (1) บันทึกแถวที่ล้มเหลวและสาเหตุ (มีอยู่แล้วใน `reportJson`)
(2) แจ้ง Owner/ผู้ให้ข้อมูลต้นทางให้แก้ไขไฟล์ต้นฉบับ (3) เริ่ม Step 3 ใหม่ (Preview) ด้วยไฟล์ที่
แก้ไขแล้ว โดยไม่ต้อง rollback ระดับฐานข้อมูลทั้งชุด

## 7. Rollback — ระดับที่ 2: ทั้งฐานข้อมูล (Disaster Recovery)

**เมื่อไหร่ใช้** (Rollback Triggers — เกณฑ์ชัดเจน ไม่ใช่ความรู้สึก):

- พบข้อมูลเสียหาย/ผิดพลาดที่ **ไม่ได้เกิดจาก job นำเข้าเอง** (เช่น bug ที่กระทบข้อมูลเดิมที่มีอยู่
  ก่อน cutover ด้วย)
- Checkpoint #2 ไม่ผ่าน **และ** ปัญหาลามเกินขอบเขตของ job เดียว (เช่น constraint violation ที่
  บ่งชี้ schema ไม่ตรงกับที่ออกแบบไว้)
- พบเหตุการณ์ด้านความปลอดภัยระหว่าง freeze window (ดูข้อยกเว้นฉุกเฉิน §3)
- On-call รายงานว่า `/api/health` ตอบ `503`/`degraded` ต่อเนื่องหลัง cutover โดยหาสาเหตุไม่ได้
  ภายใน 15 นาที

**ขั้นตอน** (ใช้ `scripts/db-restore.mjs` — พิสูจน์จริงใน `readiness-checklist.md` §4.2):

1. Release Manager ประกาศ ROLLBACK — freeze window ขยายต่อจนกว่าจะยืนยันฐานข้อมูลกลับสู่สภาพ
   ก่อน cutover สำเร็จ
2. DB Operator รัน:
   ```
   node scripts/db-restore.mjs --file <backup จาก Step 1 ของ §5> \
     --target-db <ชื่อฐานข้อมูล production จริง> --confirm-overwrite
   ```
   (ต้องใช้ `--confirm-overwrite` เพราะเป็นการเขียนทับฐานข้อมูลที่ `DATABASE_URL` ชี้ไปจริง —
   double opt-in ตามที่สคริปต์ออกแบบไว้โดยตั้งใจ เพื่อไม่ให้ restore ทับข้อมูลจริงโดยไม่ตั้งใจ)
3. เทียบ row count ของตาราง Restricted หลัก (users/organizations/persons/audit_logs เป็นอย่างน้อย)
   ระหว่างฐานข้อมูลที่กู้คืนกับตัวเลขที่บันทึกไว้ตอน backup (Step 1 ของ §5) — ต้องตรงกันทุกตัวเลข
   เหมือนวิธีที่พิสูจน์แล้วในหัวข้อ 4.2 ของ `readiness-checklist.md`
4. รัน smoke test ซ้ำ (Step 5 ของ §5) เพื่อยืนยันระบบทำงานปกติหลัง rollback
5. แจ้ง Owner ทันทีพร้อมสาเหตุ + แผนแก้ไขก่อนพยายาม cutover ครั้งถัดไป
6. **ไม่พยายาม cutover ซ้ำในวันเดียวกัน** — ต้องกลับไปที่ §1 (Preconditions) ใหม่ทั้งหมด รวมถึง
   dry-run rehearsal ซ้ำกับไฟล์ข้อมูลที่แก้ไขสาเหตุแล้ว

---

## 8. Post-Cutover Verification

- [ ] Row count ของทุกตารางที่เกี่ยวข้องตรงกับผลรวมที่ `real-data-mapping.md` คาดไว้
- [ ] สุ่มตรวจข้อมูล N รายการ (แนะนำ ≥ 10 หรือ 5% ของจำนวนแถวที่นำเข้า แล้วแต่ค่าใดมากกว่า) เทียบ
      กับไฟล์ต้นฉบับด้วยตาโดยตรง (ไม่ใช่แค่เชื่อ `reportJson`)
- [ ] `audit_logs` มีแถวใหม่ตรงจำนวนกับ operation ที่เกิดขึ้นจริง (create/update ตามที่คาด)
- [ ] สุ่มทดสอบ login + สิทธิ์การเข้าถึงของแต่ละ role ที่เกี่ยวข้องกับข้อมูลที่เพิ่งนำเข้า (เช่น
      Regional Admin เห็นเฉพาะองค์กรในขอบเขตของตนตามข้อมูลจริงที่เพิ่งเข้ามาใหม่)
- [ ] `/api/health` และ `/api/admin/system/metrics` ตอบค่าปกติต่อเนื่องอย่างน้อย 30 นาที
- [ ] ไม่มี error log ผิดปกติ (ตรวจด้วยมือ เนื่องจากยังไม่มี log aggregation อัตโนมัติ)

## 9. Monitoring ระหว่างและหลัง Cutover

**ข้อจำกัดสำคัญที่ต้องรับทราบ**: โครงการนี้ **ยังไม่มีระบบ alerting/paging อัตโนมัติ**
(`ops-runbook.md` §5, `adr/0007-logging-monitoring.md`) — การเฝ้าระวังระหว่าง cutover จึงเป็น
**การ poll ด้วยมือ** ไม่ใช่ระบบแจ้งเตือนอัตโนมัติ:

| ช่วงเวลา | ความถี่ poll | ตรวจอะไร |
|---|---|---|
| ระหว่าง Step 3-6 (§5) | ทุก 2-3 นาที | `/api/health`, ผลลัพธ์แต่ละ step ตรงตามเกณฑ์ผ่านหรือไม่ |
| Post-cutover observation (T+ ถึง T+2h) | ทุก 15 นาที | `/api/health`, `/api/admin/system/metrics`, error log |
| หลังปลด freeze | กลับสู่รอบปกติของทีม | — |

หากในอนาคตมีการติดตั้งระบบ log aggregation/alerting จริง (ตามที่ระบุใน `readiness-checklist.md`
หัวข้อ 5 ข้อ 6) ให้ปรับตารางนี้เป็นการแจ้งเตือนอัตโนมัติแทนการ poll ด้วยมือ

## 10. แผนการสื่อสาร

| เหตุการณ์ | แจ้งใคร | เมื่อไหร่ |
|---|---|---|
| ประกาศเริ่ม freeze window | ทีมทั้งหมด + Owner | T-24h |
| เริ่ม cutover จริง (T0) | ทีมที่เกี่ยวข้อง | ทันทีที่เริ่ม Step 0 |
| Checkpoint #1/#2 ผ่าน/ไม่ผ่าน | Release Manager → ทีม | ทันทีหลังแต่ละ checkpoint |
| Rollback (ถ้าเกิดขึ้น) | ทีมทั้งหมด + Owner ทันที | ทันทีที่ตัดสินใจ rollback |
| จบ cutover / ปลด freeze | ทีมทั้งหมด + Owner | หลัง Step 8 |

ช่องทางจริง (อีเมล/แชท/ที่ประชุม) ยังไม่ถูกกำหนดในเอกสารระดับโครงการที่มีอยู่ — ทีมต้องตกลงก่อนใช้
เอกสารนี้ครั้งแรก (ดูหัวข้อ 12 งานถัดไปที่ควรทำ)

## 11. Sign-off และรายงานหลัง Cutover

หลังจบทุกขั้นตอน (ไม่ว่าจะสำเร็จหรือ rollback) ต้องบันทึกรายงานแยกฉบับ (รูปแบบเดียวกับ
`migration-dry-run-report.md`) ประกอบด้วยอย่างน้อย: เวลาเริ่ม/จบจริง, ผลของแต่ละ checkpoint,
จำนวนแถวที่นำเข้าจริง (created/matched/failed), เหตุการณ์ผิดปกติที่พบ (ถ้ามี), การตัดสินใจ
break-glass ใดๆ (ถ้ามี, ดู §3), และลายเซ็น/การรับทราบของ Owner

---

## 12. ขอบเขตที่ตัดออกและข้อจำกัด (Out of Scope — ต้องแจ้ง Owner)

- **ไม่มีระบบอัตโนมัติสำหรับ trigger rollback** — การตัดสินใจ rollback เป็นการตัดสินใจของมนุษย์
  (Release Manager) ตามเกณฑ์ใน §7 เสมอ ไม่มี script ที่ rollback ให้เองอัตโนมัติเมื่อ metric ผิดปกติ
- **ไม่มีการกำหนดช่องทางสื่อสารจริง** (ดู §10) — ต้องตกลงก่อนใช้งานเอกสารนี้ครั้งแรก
- **ยังไม่เคยซ้อม (rehearsal) เอกสารทั้งฉบับนี้เลย** — สถานะ Freeze Window ใน
  `readiness-checklist.md` เป็น Pending ด้วยเหตุผลนี้โดยตรง
- **ไม่ครอบคลุมการนำเข้าข้อมูลชนิดอื่นนอกเหนือจาก Excel Import Pipeline ที่มีอยู่** (เช่น ถ้าในอนาคต
  มีแหล่งข้อมูลจริงชนิดอื่นที่ไม่ผ่าน pipeline นี้ ต้องออกแบบขั้นตอนแยกต่างหาก)

## 13. งานถัดไปที่ควรทำ

1. ซ้อม (rehearse) เอกสารนี้ทั้งฉบับกับข้อมูลจำลองขนาดใกล้เคียงข้อมูลจริง อย่างน้อย 1 ครั้ง
2. ตกลงช่องทางสื่อสารจริงสำหรับ §10
3. เมื่อ `readiness-checklist.md` เปลี่ยนเป็น GO: กำหนดวัน cutover จริงร่วมกับ Owner แล้วเริ่มจาก
   §4 (Pre-Cutover Checklist) ของเอกสารนี้
4. พิจารณาออกแบบ automated rollback trigger เมื่อมีระบบ monitoring/alerting จริงในอนาคต (ปัจจุบัน
   เป็น manual ทั้งหมดตามข้อจำกัด §12)
