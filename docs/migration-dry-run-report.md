## 1. การออกแบบ: ระดับการแยก (Isolation Level) ของสำเนาที่ลดความเสี่ยง

### 1.1 เปรียบเทียบกับ Staging Deployment (Task 22)

| มิติ | Staging Deployment (Task 22, prisma/staging-deployment.md) | Dry-run Migration (งานนี้) |
|---|---|---|
| PostgreSQL | cluster แยกต่างหาก (`staging`, port 5433) | **ฐานข้อมูลแยกในคลัสเตอร์เดิม** (`main`, port 5432) |
| Role | `sangha_staging` (least-privilege) | `sangha_dryrun` (least-privilege เหมือนกัน) |
| แอปพลิเคชัน | production standalone build (`node .next/standalone/server.js`) | `next dev` instance ที่สอง (ดูเหตุผลใน §1.3) |
| เป้าหมาย | พิสูจน์ deployment parity เต็มรูปแบบ (CI/CD, container, env separation) | พิสูจน์ reconcile/duplicate/rollback ของการนำเข้าข้อมูลเท่านั้น |

**เหตุผลที่เลือกระดับเบากว่า**: เป้าหมายของบรีฟงานนี้คือ "ลดความเสี่ยงของการซ้อมนำเข้า
ข้อมูล" ไม่ใช่ "พิสูจน์ deployment parity" (นั่นคืองานของ Task 22 ที่เสร็จไปแล้ว) — สิ่งที่
ต้องแยกออกจากข้อมูลจริงอย่างเด็ดขาดคือ **ฐานข้อมูล** เท่านั้น (ที่ที่ผลการนำเข้าจะถูกเขียน
จริง) ส่วน "แอปพลิเคชันตัวไหนคุยกับฐานข้อมูลนั้น" ไม่จำเป็นต้องแยกระดับ deployment เต็ม
รูปแบบ — คนละ role + คนละฐานข้อมูล + คนละ credential ก็เพียงพอแล้วที่จะรับประกันว่าการ
ซ้อมนี้ **ไม่มีทางเขียนไปโดนข้อมูลจริงได้เลยแม้จะมีบั๊กในสคริปต์ทดสอบเอง** (defense in
depth: ผิดพลาดที่แอปพลิเคชัน → ยังมี credential/role คนละตัวกันกั้นไว้อีกชั้น)

### 1.2 การจัดเตรียม (`scripts/dry-run-db.sh`)

```
scripts/dry-run-db.sh up     # สร้าง role+database ใหม่ + migrate --reset + seed
scripts/dry-run-db.sh down   # ลบ database+role ทิ้งถาวร
scripts/dry-run-db.sh url    # พิมพ์ DATABASE_URL (ไม่ commit — เก็บรหัสผ่านที่สุ่มใหม่
                              # ทุกครั้งไว้ใน .env.dryrun.local ซึ่งเข้ากติกา ".env*" ใน
                              # .gitignore อยู่แล้ว ไม่ต้องแก้ไฟล์ .gitignore เพิ่ม)
```

`up` idempotent-safe (ตรวจว่า role/database มีอยู่แล้วก่อนสร้างซ้ำ, sync password ทุกครั้ง)
— รันซ้ำได้โดยไม่มีผลข้างเคียง ใช้ `node prisma/dev-migrate-verify.mjs --reset` (สคริปต์
เดียวกับที่ Task 2 เป็นต้นมาใช้ทดสอบ migration จริงทุกงาน — ดู prisma/MIGRATIONS.md
"ข้อจำกัดของเครื่องมือ" เรื่อง Prisma CLI ใช้งานไม่ได้จริงในสภาพแวดล้อมนี้) เพื่อ replay
migration ทั้ง **20 ไฟล์** จากศูนย์ แล้ว seed baseline ด้วย `prisma/seed.ts` ตัวเดียวกับ
dev/test ทุกงานก่อนหน้า (ให้มี ACTIVE appointment ของจริงให้แถวทดสอบชนกับข้อมูลจริงได้ —
ดู §3)

Task 22 (prisma/staging-deployment.md §5.3) และ prisma/audit-history.md §4 บันทึกไว้ว่า

บันทึกไว้โปร่งใสตามข้อจำกัด "ห้ามอ้างว่าทดสอบผ่านหากยังไม่ได้รันจริง" (รันจริงแล้วพบปัญหา
จริง แก้แล้วรันซ้ำจนผ่านจริง ไม่ใช่แก้ตัวเลขคาดการณ์ให้ตรงกับผลลัพธ์ผิดๆ):

1. **`skippedRowCount` เข้าใจผิดความหมาย**: คาดว่า "ข้าม/ล้มเหลว" (`job.skippedRowCount`)
   จะเท่ากับจำนวนแถวที่ล้มเหลวเฉพาะตอน commit (2 แถว) แต่ตรวจโค้ดจริงใน
   `src/app/actions/import.ts::commitImportJobAction` พบว่า `skippedRowCount =
   outcomes.length - committedRowCount` โดย `outcomes` ครอบคลุม **ทุกแถวที่ re-validate
   ตอน commit** (ทั้งแถวที่ผ่านและไม่ผ่านตอน preview) ไม่ใช่แค่แถวที่ผ่าน preview แล้วไป
   ล้มเหลวตอน commit เท่านั้น — ค่าจริงจึงเป็น `totalRows - committedOk = 19 - 7 = 12`
   ไม่ใช่ 2 แก้โดยเพิ่ม `skippedRowCountUI` ใน `summarizeExpectations()` ให้คำนวณตามสูตรนี้
   ตรงๆ พร้อม comment อธิบายที่มา
2. **การนับข้อความบนหน้าเว็บด้วย `getByText().count()` ไม่แม่นยำสำหรับข้อความสั้นที่อาจ
   เป็น substring ของข้อความอื่น**: แถว BADSTATUS-01 คาดว่าข้อความ "ไม่ถูกต้อง" จะปรากฏ
   1 ครั้ง แต่นับได้ 2 ครั้ง — ตรวจสอบ `reportJson` ที่บันทึกจริงในฐานข้อมูลยืนยันว่ามี
   เพียงข้อความเดียวเท่านั้นที่มีคำนี้ (`สถานะการแต่งตั้ง "BOGUS_DRYRUN" ไม่ถูกต้อง...`) —
   จุดที่สองที่นับได้เพิ่มมาจากโครงสร้างการ render บนหน้าเว็บ (ไม่ใช่ธุรกิจ logic ผิด)
   ไม่ได้ไล่หาสาเหตุการ render ต่อ (ไม่กระทบความถูกต้องของข้อมูล) แต่ **เปลี่ยนวิธีทดสอบ
   ทั้งหมดในไฟล์นี้จากการนับข้อความบน DOM มาเป็นการตรวจ `reportJson` ที่บันทึกจริงใน
   ฐานข้อมูลโดยตรงแทน** ซึ่งแม่นยำกว่าและเป็นแหล่งความจริงที่ backend ใช้จริง (ยังคงเหลือ
   assertion แบบ UI-visible ไว้บางจุดแบบ "ปรากฏอยู่จริงหรือไม่" (`textAppears`, ไม่นับ
   จำนวน) เพื่อยืนยันว่าหน้าเว็บ render ผลลัพธ์ให้ผู้ใช้เห็นจริง)

ทั้งสองจุดแก้ไขแล้วและรันซ้ำจนได้ 101/101 PASSED ตามที่รายงานใน §3

### 5.2 ประเด็นที่พบระหว่างงานนี้: referenceCode ตรงกับ DB แต่ชื่อในไฟล์ไม่ตรงกัน — ไม่มี
คำเตือนใดๆ ให้ผู้ใช้เห็น (แถว MISMATCH-01)

`buildImportLookups()` (`src/lib/import-pipeline.ts`) ดึงข้อมูล `personsByReferenceCode`
จากฐานข้อมูลมาเตรียมไว้จริง (query เพิ่มเติมโดยเฉพาะ) แต่ตรวจสอบโค้ดทั้งไฟล์แล้วพบว่า
**ไม่มีจุดใดใน `validateAllRows()` เรียกใช้ `lookups.personsByReferenceCode` เลย** — ฟังก์ชัน
นี้ตรวจความสอดคล้องของ referenceCode เฉพาะ **ภายในไฟล์เดียวกัน** เท่านั้น (ตัวแปร
`referenceCodeSeen` ที่ผูกกับแถวอื่นในไฟล์นี้) ไม่เคยเทียบกับชื่อที่บันทึกไว้จริงใน
ฐานข้อมูลเลย

ผลคือ: ถ้าไฟล์นำเข้าระบุ `referenceCode` ตรงกับบุคคลที่มีอยู่แล้ว แต่ `prefix`/`fullName`
ในไฟล์ **ไม่ตรง** กับที่บันทึกไว้จริง (เช่น พิมพ์ผิด หรือใช้รหัสอ้างอิงผิดคน) — แถวนั้นจะ
**ผ่าน validate โดยไม่มีคำเตือนใดๆ ปรากฏให้ผู้ตรวจสอบเห็นที่หน้า preview เลย** และตอน commit
`findOrCreatePersonWithClient()` จะจับคู่กับบุคคลเดิมตามปกติ (พฤติกรรมนี้ปลอดภัยในแง่ข้อมูล
— ไม่มีการ overwrite ข้อมูลเดิม ยืนยันด้วยการทดสอบจริงว่า MOCKP-002 ยังเป็น
`พระครู`/`พระครูสมมติ ธมฺมรกฺขิโต (ข้อมูลจำลอง)` เหมือนเดิมทุกประการหลัง commit) **แต่ผู้
ดำเนินการนำเข้าจะไม่มีทางรู้เลยว่าไฟล์ของตนอ้างอิงคนละคนกับที่ระบบเข้าใจ** จนกว่าจะไปเปิด
ดูข้อมูลบุคคลนั้นเองภายหลัง

**นี่คือสิ่งที่แบบฝึกซ้อม dry-run ควรค้นพบพอดี** (ตามเจตนาของบรีฟ "reconcile counts,
duplicates") — ไม่ใช่ความเสี่ยงต่อความถูกต้องของข้อมูล (data integrity ยังคงอยู่) แต่เป็น
ความเสี่ยงด้าน **การมองเห็นระหว่าง reconciliation จริง** เมื่อมีข้อมูลจริงหลายพันแถว
โอกาสที่จะมี referenceCode พิมพ์ผิดแล้วจับคู่กับคนละคนโดยไม่มีใครสังเกตเห็นจะสูงขึ้นมาก

**ขอบเขตงานนี้**: บรีฟระบุ "แก้เฉพาะไฟล์ที่เกี่ยวข้องกับงานนี้" — `src/lib/import-pipeline.ts`
เป็นไฟล์จากงาน P7 (Task 16) ไม่ใช่ขอบเขตของงาน dry-run/ซ้อมนี้โดยตรง จึง**ไม่แก้ไข
`import-pipeline.ts` ในงานนี้** แต่บันทึกไว้เป็นข้อค้นพบสำคัญ พร้อมข้อเสนอแนะสำหรับงานถัดไป
(ดู §9) — สอดคล้องกับแนวทางเดียวกับที่ Task 23 พบ "Person model เป็น stub" แล้วบันทึกเป็น
Known Gap แทนที่จะแก้ schema ในงานที่ไม่ใช่ขอบเขต

## 7. Rollback — ผลการพิสูจน์

พิสูจน์ rollback 2 ระดับ:

1. **ระดับแถว (application-level, ผ่าน `withTransaction`)**: แถว DBCONFLICT-01 และ
   UNIQUEFILE-01 (ไม่มี `referenceCode`) พยายามสร้าง Person ใหม่ก่อน แล้วจึงพยายามสร้าง
   Appointment ซึ่งล้มเหลวเพราะชนกับ ACTIVE appointment เดิมใน DB — ทั้งแถวถูก ROLLBACK
   อัตโนมัติจาก `withTransaction()` (`src/lib/db.ts`) พิสูจน์ด้วย SQL ตรงว่า **ไม่มี Person
   ที่มีชื่อของทั้งสองแถวนี้หลงเหลืออยู่ในฐานข้อมูลเลย** (ถ้า rollback ไม่ทำงานจริง จะพบ
   Person กำพร้าที่ไม่มี Appointment คู่กัน)
2. **ระดับ DB trigger (`import_jobs_prevent_terminal_mutation`)**: ทดสอบซ้ำแบบเดียวกับ
   `prisma/test-import-pipeline.mjs` Part 6 บนฐานข้อมูล dry-run ที่ replay migration ใหม่
   ล้วนๆ — ยืนยันว่า trigger ถูกสร้างถูกต้องจาก `migration.sql` จริง (ไม่ใช่ผลพลอยได้จาก
   สถานะเก่าสะสมใน dev DB) และ atomic claim (`claimJobForCommit`) ยังคง idempotent-safe
   ต่อการยิงพร้อมกันเหมือนเดิม

## 9. Failure Mode และ Recovery

| ขั้นตอน | Failure Mode | Recovery |
|---|---|---|
| `scripts/dry-run-db.sh up` ล้มเหลวกลางทาง (เช่น migration บางไฟล์ error) | ฐานข้อมูล/role อาจค้างอยู่ในสถานะไม่สมบูรณ์ | รัน `scripts/dry-run-db.sh down` แล้ว `up` ใหม่ได้ทันที (idempotent — `down` ใช้ `IF EXISTS` ทุกคำสั่ง) |
| dev server ตัวที่สอง (:3100) ชี้ผิดฐานข้อมูลโดยไม่ตั้งใจ | อาจเขียนข้อมูลทดสอบไปโดนฐานข้อมูลผิด | ป้องกันด้วยการตรวจ `/proc/<pid>/environ` ก่อนเริ่มทดสอบทุกครั้ง (ดู §1.3) — ถ้าไม่ตรง ให้ kill แล้วเปิดใหม่พร้อม `DATABASE_URL` ที่ถูกต้อง ก่อนรันไฟล์ทดสอบใดๆ |
| การซ้อม commit ล้มเหลวกลางแถว (เช่น process ถูก kill ระหว่าง transaction) | ไม่มีความเสี่ยงต่อความสมบูรณ์ของข้อมูล — `withTransaction()` ใช้ BEGIN/COMMIT/ROLLBACK จริงที่ระดับ PostgreSQL connection เดียว ถ้า process ตายกลางทาง connection หลุด PostgreSQL จะ ROLLBACK อัตโนมัติ | ตรวจสถานะ job ที่ `import_jobs.status` — ถ้าค้างที่ `COMMITTING` (ไม่ถึง `COMMITTED`) แถวที่ยังไม่ถูก process จะยังไม่ถูกเขียน สามารถลบ job ทดสอบทิ้งแล้วเริ่มใหม่ได้ปลอดภัย (เป็นฐานข้อมูล dry-run ที่ทิ้งได้อยู่แล้ว) |
| ลืมรัน `scripts/dry-run-db.sh down` หลังทำงานเสร็จ | ฐานข้อมูล/role ทดสอบค้างอยู่ในคลัสเตอร์เดิมกับ dev (ไม่กระทบข้อมูลจริงเพราะคนละฐานข้อมูล/role แต่เปลืองทรัพยากรและอาจสร้างความสับสน) | รัน `scripts/dry-run-db.sh down` เมื่อใดก็ได้ภายหลัง — ปลอดภัยเสมอเพราะแยกฐานข้อมูล/role จาก `sangha_system_dev` อย่างสมบูรณ์ ตรวจสอบก่อนลบด้วย `sudo -u postgres psql -c "\\l"` ถ้าต้องการความมั่นใจเพิ่มเติม |

## 10. ความเสี่ยง/ข้อจำกัด

   ที่ขอบเขตนี้ในงานถัดไปที่เกี่ยวกับ performance ของ import pipeline)
4. **Person model ยังเป็น stub** (ไม่มีเลขบัตรประชาชน/วันเกิด/ประวัติอุปสมบท ฯลฯ — ดู
   prisma/real-data-mapping.md §1.5) — ข้อจำกัดนี้ยังคงเป็น blocker หลักสำหรับการนำเข้า
   ทะเบียนจริงแบบเต็มรูปแบบ ไม่เกี่ยวกับงาน dry-run นี้โดยตรงแต่ยังไม่ถูกแก้ไข

## 11. งานถัดไปที่ควรทำ

1. **แก้ไขประเด็น MISMATCH-01** (`src/lib/import-pipeline.ts::validateAllRows`) — เพิ่มการ
   ใช้ `lookups.personsByReferenceCode` ที่มีอยู่แล้ว (แต่ยังไม่ถูกเรียกใช้เลยในโค้ดปัจจุบัน)
   เปรียบเทียบ `prefix`/`fullName` ในไฟล์กับที่บันทึกไว้จริง แล้วแสดงเป็น**คำเตือน**ที่หน้า
   preview (ไม่ใช่ error ที่บล็อกการนำเข้า เพราะอาจเป็นการอัปเดตข้อมูลที่ตั้งใจจริง เช่น
   เปลี่ยนคำนำหน้าหลังอุปสมบทซ้ำ) เพื่อให้ผู้ตรวจสอบเห็นและตัดสินใจเองว่าจะดำเนินการต่อ
   หรือแก้ไฟล์ก่อน
2. **ทดสอบ performance ที่ปริมาณข้อมูลใกล้เคียงของจริง** (หลักพันแถว, ใกล้ `IMPORT_MAX_ROWS`)
   บนสำเนา dry-run เดียวกันนี้ — วัดเวลาที่ใช้ในขั้นตอน parse/validate/commit แต่ละขั้น
3. **ผูก scope `OWN_ORG_SUBTREE` เข้ากับ UI ของ `/admin/import`** (ยังเป็นข้อจำกัดที่รู้อยู่
   แล้วตั้งแต่ Task 16 — REGIONAL_ADMIN/REGISTRAR_STAFF ยังถูกปฏิเสธเข้าทั้งหน้าแม้จะควรมี
   สิทธิ์นำเข้าเฉพาะหน่วยงานย่อยของตนในอนาคต)
4. **ดำเนินการตาม Real-data Readiness Gate checklist** (prisma/data-policy.md) — งานนี้เป็น
   หนึ่งในเงื่อนไขที่ผ่านแล้ว (dry-run migration สำเร็จ) ยังเหลือรายการอื่นตาม gate ที่ต้อง
   ตรวจสอบก่อนนำเข้าข้อมูลจริง (ดู prisma/real-data-mapping.md §8 รายการงานถัดไป 7 ข้อ)
5. **พิจารณาเพิ่มการทดสอบ concurrent commit ผ่าน UI จริง** (สอง browser context กดยืนยันงาน
   เดียวกันพร้อมกันจริงๆ ผ่าน browser ไม่ใช่แค่ราw SQL) เพื่อพิสูจน์ UX ของข้อความ error
   ที่ผู้ใช้จะเห็นจริงเมื่อกดปุ่มซ้ำสองครั้งเร็วๆ (ปัจจุบันพิสูจน์ผ่าน raw SQL เท่านั้นตาม
   precedent เดิมของ Task 16)
