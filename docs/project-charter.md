# Project Charter

**โครงการ:** ระบบฐานข้อมูลคณะสงฆ์และการศึกษาพระปริยัติธรรม (นักธรรม / ธรรมศึกษา / บาลี) พร้อมคลังข้อสอบ ระบบแบบทดสอบ ระบบสมาชิก และระบบผู้ดูแลระบบ
**เฟสปัจจุบัน:** P0 — Orientation & Safety
**สถานะเอกสาร:** ร่างสำหรับ Owner Review (ยังไม่ผ่านการอนุมัติ)
**เวอร์ชัน:** 0.1
**วันที่จัดทำ:** 2026-09-14
**ผู้จัดทำ:** ทีมงาน (Product Owner / Architect / Engineering / QA-Security ตามบทบาทที่ได้รับมอบหมาย)
**ผู้อนุมัติ (Owner):** รอการระบุชื่อ/ตำแหน่งผู้มีอำนาจอนุมัติ

> เอกสารนี้ใช้ **ข้อมูลสมมติเท่านั้น** ไม่มีชื่อบุคคล วัด หรือหน่วยงานจริงปรากฏอยู่ในตัวอย่างใด ๆ ในเอกสารฉบับนี้

---

## 1. ภาพรวมและที่มา (Background)

องค์กรมีความประสงค์จัดทำระบบสารสนเทศเพื่อสนับสนุนงานด้านการปกครองคณะสงฆ์และการศึกษาพระปริยัติธรรม 3 สายหลัก คือ **นักธรรม**, **ธรรมศึกษา** และ **บาลี** โดยระบบจะครอบคลุมตั้งแต่ทะเบียนบุคคล/หน่วยงาน คลังข้อสอบส่วนกลาง ระบบจัดสอบและประมวลผล ไปจนถึงระบบสมาชิกและเครื่องมือบริหารจัดการสำหรับผู้ดูแลระบบ

โครงการนี้เกี่ยวข้องในเชิงบริบท (ไม่ใช่ส่วนหนึ่งของขอบเขตงาน) กับงานสารนิพนธ์ด้านโลจิสติกส์การขนส่งพัสดุของสำนักงานแม่กองธรรมสนามหลวงที่ดำเนินการคู่ขนานอยู่ — ทั้งสองงานอยู่ในบริบทองค์กรเดียวกันแต่เป็นคนละขอบเขตงานและคนละผลลัพธ์ที่ต้องส่งมอบ

## 2. วิสัยทัศน์ (Vision Statement)

สร้างระบบสารสนเทศกลางที่น่าเชื่อถือ ตรวจสอบย้อนหลังได้ (auditable) และปลอดภัย สำหรับบริหารข้อมูลคณะสงฆ์และกระบวนการศึกษา/สอบพระปริยัติธรรม ลดงานเอกสารกระดาษและงานคีย์ข้อมูลซ้ำซ้อน และให้สิทธิ์การเข้าถึงข้อมูลตามลำดับชั้นการปกครองคณะสงฆ์อย่างถูกต้องแม่นยำ

## 3. เป้าหมายโครงการ (Goals)

| # | เป้าหมาย |
|---|---|
| G1 | มีทะเบียนกลางของพระภิกษุ/สามเณร วัด และสำนักเรียน พร้อมโครงสร้างสายการปกครอง (ภาค/จังหวัด/อำเภอ/ตำบล) ที่เป็นแหล่งข้อมูลจริงหนึ่งเดียว (single source of truth) |
| G2 | รองรับการศึกษา 3 สายงาน (นักธรรม, ธรรมศึกษา, บาลี) ครบทุกระดับชั้น พร้อมคลังข้อสอบส่วนกลางที่ค้นหา จัดหมวดหมู่ และควบคุมเวอร์ชันได้ |
| G3 | มีระบบจัดสอบ/แบบทดสอบที่รองรับทั้งการสอบจริงระดับสนามสอบและแบบฝึกหัดออนไลน์ พร้อมกระบวนการตรวจให้คะแนนและประกาศผลที่ตรวจสอบย้อนหลังได้ |
| G4 | มีระบบสมาชิกและสิทธิ์การเข้าถึงหลายระดับ (multi-level RBAC) ที่ยึดหลัก deny-by-default และบังคับใช้ฝั่งเซิร์ฟเวอร์ทุกจุด |
| G5 | มีเครื่องมือผู้ดูแลระบบสำหรับบริหารผู้ใช้ สิทธิ์ ข้อมูลอ้างอิง และตรวจสอบ audit log |
| G6 | นำเข้าข้อมูลจำนวนมากผ่านไฟล์ Excel ได้อย่างปลอดภัย มี validation รายแถว และรายงานข้อผิดพลาดที่นำไปแก้ไขต่อได้ |
| G7 | จัดเก็บไฟล์ (ใบประกาศนียบัตร เอกสารแนบ ไฟล์ข้อสอบ) ผ่าน PDF/Object Storage อย่างปลอดภัยและเชื่อมโยงกับข้อมูลต้นทางได้ |
| G8 | ทุกการเปลี่ยนแปลงข้อมูลสำคัญมีประวัติ (history/audit) ไม่เขียนทับข้อมูลเดิม และ operation ที่ต้อง atomic ใช้ transaction เสมอ |

## 4. สิ่งที่ไม่อยู่ในขอบเขต (Non-Goals) — สำหรับเฟส P0–P1 ปัจจุบัน

| # | รายการ | เหตุผล |
|---|---|---|
| N1 | แอปพลิเคชันมือถือ (native mobile app) | เริ่มต้นเป็น web application (Next.js) ก่อน; ประเมินความจำเป็นภายหลัง |
| N2 | Public open API สำหรับบุคคลภายนอก | ต้องผ่านการออกแบบ security/rate-limit เพิ่มเติม อยู่นอกขอบเขต P0–P1 |
| N3 | ระบบชำระเงิน/รับบริจาคออนไลน์ | ไม่ปรากฏในความต้องการปัจจุบัน; หากมีในอนาคตต้องเปิดโครงการย่อยแยก |
| N4 | การเชื่อมต่อฮาร์ดแวร์สนามสอบ (เครื่องสแกนลายนิ้วมือ/บัตรประจำตัว) | อยู่นอกขอบเขตด้านเทคโนโลยีที่กำหนด |
| N5 | การโยกย้ายข้อมูลจริงจากระบบเดิม (data migration จากระบบ production เดิม) | ต้องรอผ่าน **Real-data Readiness Gate** (ดูข้อ 9) ก่อนจึงจะเริ่มวางแผนได้ |
| N6 | การรองรับภาษาอื่นนอกเหนือจากไทย/อังกฤษในชั้น UI | ยังไม่ระบุความต้องการ |
| N7 | Real-time chat/notification แบบ push ระหว่างผู้ใช้ | ไม่อยู่ในคำขอปัจจุบัน |

Non-goals ข้างต้นสามารถย้ายเข้าสู่ขอบเขต (in-scope) ได้ในเฟสถัดไป หากเจ้าของโครงการอนุมัติการเปลี่ยนแปลงขอบเขตอย่างเป็นทางการ

## 5. ผู้มีส่วนได้ส่วนเสียและกลุ่มผู้ใช้งาน (Actors) — สรุป

รายละเอียดครบถ้วนของแต่ละ Actor (สิทธิ์, ขอบเขตข้อมูลที่เข้าถึงได้) อยู่ใน `requirements.md` ส่วนที่ 3 สรุปโดยย่อ:

1. **Super Admin** — ผู้ดูแลระบบสูงสุด ตั้งค่าระบบและจัดการสิทธิ์ทั้งหมด
2. **เจ้าหน้าที่ส่วนกลาง (สำนักงานแม่กองธรรม/บาลีสนามหลวง)** — บริหารข้อมูลอ้างอิง คลังข้อสอบ และภาพรวมทั้งระบบ
3. **ผู้บริหารคณะสงฆ์ตามลำดับชั้น (ภาค/จังหวัด/อำเภอ/ตำบล)** — เข้าถึงและจัดการข้อมูลเฉพาะเขตปกครองของตน
4. **เจ้าหน้าที่ธุรการสำนักเรียน/วัด** — บันทึกและปรับปรุงข้อมูลระดับปฏิบัติการ (คีย์ข้อมูล, อัปโหลดเอกสาร)
5. **ครูสอนธรรม/ครูสอนบาลี** — เสนอ/ทบทวนข้อสอบ ติดตามผลนักเรียนในความรับผิดชอบ
6. **ผู้ตรวจข้อสอบ/กรรมการคุมสอบ** — บันทึกคะแนน จัดการรอบสอบ
7. **นักเรียน/ผู้เข้าสอบ** — ดูข้อมูลของตนเอง สมัครสอบ ทำแบบฝึกหัด ดูผลสอบ
8. **ผู้ตรวจสอบภายใน (Auditor)** — สิทธิ์อ่านอย่างเดียวสำหรับ audit log และรายงาน
9. **บุคคลทั่วไป (Guest)** — เข้าถึงเฉพาะข้อมูลสาธารณะที่กำหนดไว้ชัดเจน (เช่น ตรวจสอบผลสอบด้วยเลขที่กำหนด หากอนุมัติให้เปิดเผย)
10. **System/Scheduled Jobs** — งานอัตโนมัติ เช่น ประมวลผลไฟล์นำเข้า Excel แบบ batch, สร้างรายงานตามกำหนดเวลา

| M2. หลักสูตรและระดับการศึกษา | นักธรรม (ตรี/โท/เอก), ธรรมศึกษา (ตรี/โท/เอก), บาลี (ประโยค 1–9), สนามสอบ |
| M3. คลังข้อสอบ (Question Bank) | หมวดหมู่/ระดับ/ชนิดข้อสอบ, metadata, เวอร์ชัน, การอนุมัติ |
| M4. ระบบแบบทดสอบ/จัดสอบ (Testing Engine) | สร้างชุดข้อสอบ, สอบจริง/แบบฝึกหัด, ตรวจให้คะแนน, ประกาศผล |
| M5. ระบบสมาชิก (Membership) | สมัครสมาชิก, ยืนยันตัวตน (Auth.js), จัดการโปรไฟล์ |
| M6. ผู้ดูแลระบบ (Admin Console) | จัดการผู้ใช้/บทบาท/สิทธิ์, ตั้งค่าอ้างอิง, ดู audit log |
| M7. นำเข้าข้อมูล Excel | Import แบบ batch พร้อม validation และรายงานผล |
| M8. จัดเก็บไฟล์ (PDF/Object Storage) | ใบประกาศนียบัตร, เอกสารแนบ, ไฟล์ข้อสอบ |
| M9. สิทธิ์การเข้าถึงหลายระดับ (RBAC) | ควบคุมสิทธิ์ตามบทบาทและลำดับชั้นการปกครอง, deny-by-default |

## 7. เทคโนโลยีและสถาปัตยกรรมเบื้องต้น (Assumptions)

- Frontend/Backend: Next.js (App Router) + TypeScript
- UI: Tailwind CSS + shadcn/ui
- ฐานข้อมูล: PostgreSQL ผ่าน Prisma ORM
- Authentication/Authorization: Auth.js (ตรวจสอบสิทธิ์เพิ่มเติมฝั่ง server ทุก request ตาม deny-by-default)
- Object storage: บริการเก็บไฟล์ที่เข้ากันได้กับ S3-compatible API (ยังไม่ระบุ provider — ต้องยืนยันในเฟสถัดไป)
- Deployment/Hosting: ยังไม่ระบุ (สมมติ containerized deployment จนกว่าจะยืนยัน)
- แวดล้อมพัฒนา/ทดสอบ ใช้ **ข้อมูลสมมติเท่านั้น** จนกว่าจะผ่าน Real-data Readiness Gate

ข้อสมมติเหล่านี้ต้องได้รับการยืนยันจากเจ้าของโครงการก่อนเริ่มเฟสออกแบบสถาปัตยกรรมโดยละเอียด (P1)

| รายชื่อ/โครงสร้างระดับการศึกษาที่ถูกต้อง (นักธรรม/ธรรมศึกษา/บาลี) | ต้องยืนยันรายละเอียดระดับชั้นและเกณฑ์สอบจากหน่วยงานที่เกี่ยวข้อง | รอยืนยัน |

## 9. ข้อจำกัดด้านความปลอดภัยและข้อมูล (Safety & Data Constraints)

ข้อกำหนดต่อไปนี้มีผลบังคับใช้กับ**ทุกเฟส**ของโครงการ ไม่ใช่เฉพาะ P0:

1. **ห้ามใช้ข้อมูลบุคคลจริง**ใน seed data, screenshot, log หรือ test fixture ใด ๆ จนกว่าจะผ่าน Real-data Readiness Gate
2. **Authorization ต้องตรวจสอบฝั่ง server เสมอ** และยึดหลัก **deny-by-default** (ปฏิเสธก่อน อนุญาตเฉพาะที่กำหนดไว้ชัดเจน)
3. ข้อมูลสำคัญ (ทะเบียนพระภิกษุ, ผลสอบ, สิทธิ์ผู้ใช้) ต้องเก็บ **ประวัติการเปลี่ยนแปลง (audit/history)** และห้าม overwrite ข้อมูลเดิมโดยไม่มีร่องรอย
4. Operation ที่ต้อง atomic (เช่น การนำเข้าข้อมูลเป็นชุด, การบันทึกผลสอบพร้อมอัปเดตสถานะ) ต้องใช้ database transaction
5. **ห้าม commit secrets** ลงในโค้ด ใช้ `.env.example` เป็นแม่แบบเสมอ
6. **ห้ามระบุว่าการทดสอบผ่านหากยังไม่ได้รันจริง** ทุกรายงานผลการทดสอบต้องแนบคำสั่งที่รันจริงและผลลัพธ์ (Passed/Failed)
7. งานที่มีผลกระทบต่อข้อมูล (data-impacting operations) ต้องระบุ **failure mode และแนวทาง recovery** เสมอ
8. การแก้ไขงานแต่ละครั้งจำกัดเฉพาะไฟล์ที่เกี่ยวข้องกับงานนั้น ๆ เท่านั้น

### Real-data Readiness Gate (เงื่อนไขก่อนใช้ข้อมูลจริงได้)

ต้องผ่านทุกข้อต่อไปนี้ ก่อนจะอนุญาตให้มีข้อมูลบุคคลจริงในสภาพแวดล้อมใด ๆ:

- [ ] ได้รับการอนุมัตินโยบายคุ้มครองข้อมูลส่วนบุคคล (PDPA) จากเจ้าของโครงการ/ฝ่ายกฎหมาย
- [ ] Server-side authorization ผ่านการทดสอบ (unit + integration) ครบทุก endpoint ที่แตะข้อมูลบุคคล
- [ ] Audit logging ทำงานครบถ้วนสำหรับ create/update/delete บนตารางข้อมูลสำคัญ
- [ ] มีแผนสำรอง/กู้คืนข้อมูล (backup & restore) และผ่านการทดสอบ restore จริงอย่างน้อย 1 ครั้ง
- [ ] กำหนดนโยบายเก็บรักษา/ลบข้อมูล (data retention/erasure policy) ชัดเจน
- [ ] Owner ลงนามอนุมัติเป็นลายลักษณ์อักษร

| ความครบถ้วนของ Non-goals | มีการระบุขอบเขตที่ไม่รวมอย่างชัดเจน พร้อมเหตุผล |
| Data safety baseline | ข้อกำหนดด้านความปลอดภัยข้อมูล (ข้อ 9) ถูกบันทึกและพร้อมอ้างอิงในทุกเฟสถัดไป |

ตัวชี้วัดเชิงเทคนิค (performance, coverage, import success rate ฯลฯ) จะกำหนดค่าเป้าหมายที่วัดได้ในเฟส P2 เมื่อมีการออกแบบสถาปัตยกรรมและ non-functional requirements โดยละเอียดแล้ว (ระบุไว้เป็น placeholder ใน `requirements.md` ส่วนที่ 5)

## 11. แนวทางการทำงาน (Engineering Workflow Standard)

ทุกงานในโครงการ (ทุกเฟส ทุกโมดูล) ดำเนินตามลำดับ:

**วิเคราะห์ → ออกแบบ → ลงมือทำ → ทดสอบ → review → แก้ → regression test → commit**

และทุกฟังก์ชัน/feature ที่พัฒนาในเฟสถัดไปต้องระบุครบ 9 องค์ประกอบ: **Actor, Input, Process, Output, Permission, Validation, Error State, Audit, Acceptance Criteria** — รูปแบบ (template) และตัวอย่างที่กรอกครบอยู่ใน `requirements.md` ส่วนที่ 8

## 13. ความเสี่ยง (Risks)

| # | ความเสี่ยง | ผลกระทบ | แนวทางลดความเสี่ยง |
|---|---|---|---|
| R1 | ยังไม่ยืนยันโครงสร้างการปกครองคณะสงฆ์/ระดับการศึกษาที่ถูกต้องจากหน่วยงาน | ออกแบบ data model ผิดตั้งแต่ต้น ต้อง rework | ยืนยันกับ Owner/ผู้เชี่ยวชาญโดเมนก่อนเริ่ม P1 |
| R2 | ยังไม่เลือกผู้ให้บริการ Object Storage และ Hosting | กระทบการออกแบบสถาปัตยกรรมไฟล์แนบ | ตัดสินใจก่อนเริ่ม P1/P6 |
| R3 | ความซับซ้อนของสิทธิ์ตามลำดับชั้นการปกครอง (hierarchical RBAC) | เสี่ยงข้อมูลรั่วไหลข้ามเขตปกครองหากออกแบบผิด | ออกแบบ permission model อย่างละเอียดใน P2 พร้อมชุดทดสอบเฉพาะ |
| R4 | การนำเข้าข้อมูลจำนวนมากผ่าน Excel อาจมีข้อมูลไม่ตรงรูปแบบ | ข้อมูลเสียหาย/ซ้ำซ้อนหากไม่มี validation ที่ดี | กำหนด validation rule และ dry-run/rollback ใน M7 |
| R5 | แรงกดดันให้ใช้ข้อมูลจริงก่อนผ่าน Readiness Gate | ละเมิดข้อจำกัดข้อมูล/ความเสี่ยงด้าน PDPA | ยึด Real-data Readiness Gate เป็นเงื่อนไขบังคับ ไม่มีข้อยกเว้น |
