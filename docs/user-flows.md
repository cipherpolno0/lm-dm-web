# User Flows

**โครงการ:** ระบบฐานข้อมูลคณะสงฆ์และการศึกษาพระปริยัติธรรม (นักธรรม / ธรรมศึกษา / บาลี) พร้อมคลังข้อสอบ ระบบแบบทดสอบ ระบบสมาชิก และระบบผู้ดูแลระบบ
**เฟส:** P0 — Orientation & Safety
**อ้างอิงคู่กับ:** `sitemap.md`, `requirements.md`, `data-policy.md`, `dev-rules.md`
**สถานะ:** ร่างสำหรับ Owner Review
**เวอร์ชัน:** 0.1 | **วันที่:** 2026-09-14

> เอกสารนี้ใช้ข้อมูลสมมติเท่านั้น ไม่มีชื่อบุคคล วัด หรือหน่วยงานจริงปรากฏอยู่ ทุกฟีเจอร์ระบุครบ 9 องค์ประกอบตามรูปแบบใน `requirements.md` ข้อ 8 (Actor, Input, Process, Output, Permission, Validation, Error State, Audit, Acceptance Criteria)

## 1. วัตถุประสงค์และวิธีอ่านเอกสาร

เอกสารนี้แจกแจง 6 flow หลักของระบบ: **ข่าว, หลักสูตร, ข้อสอบ/Quiz, เอกสาร, สมัครสมาชิก, หลังบ้าน** แต่ละ flow ประกอบด้วย:

1. ภาพรวม flow (ขั้นตอนหลัก + เส้นทางผิดพลาด) อ้างอิง path จาก `sitemap.md`
2. รายการฟีเจอร์ในนั้น พร้อมสเปกครบ 9 องค์ประกอบ (รูปแบบย่อ)

ฟีเจอร์ที่มีรายละเอียดซับซ้อนกว่านี้ (เช่น การนำเข้า Excel แบบเต็ม) จะขยายเป็นสเปกฉบับยาวในเอกสารย่อยของโมดูลนั้นเมื่อเริ่มพัฒนาจริง (ดู `project-charter.md` ข้อ 12) — ตัวอย่างสเปกฉบับยาวของ Login และ Excel Import อยู่ใน `requirements.md` ข้อ 8 แล้ว จึงไม่ซ้ำในเอกสารนี้ แต่จะอ้างอิงถึง

## Flow 1 — ข่าว (News)

### 1.1 ภาพรวม
1. Guest เข้า `/news` → เห็นรายการข่าว → คลิกเข้า `/news/[slug]` → อ่านเนื้อหา
2. Central Officer/Super Admin เข้า `/admin/news` → สร้าง/แก้ไขข่าว → เผยแพร่ → ข่าวปรากฏใน `/news`
3. เส้นทางผิดพลาด: slug ไม่พบ → หน้า 404; ข่าวที่ยังไม่เผยแพร่ (draft) ต้องไม่ปรากฏใน public listing แม้ถูกเข้าถึง URL ตรง

### 1.2 ฟีเจอร์

**F1.1 — ดูรายการข่าว**
- Actor: Guest (และทุกบทบาทที่ล็อกอินแล้ว)
- Input: หน้า (page number), หมวดหมู่ (optional filter)
- Process: ดึงข่าวที่สถานะ = เผยแพร่แล้ว เรียงตามวันที่ล่าสุด แบ่งหน้า
- Output: รายการข่าว (หัวข้อ, สรุปย่อ, วันที่, ภาพปก)
- Permission: ทุกคน (Public)
- Validation: page number ต้องเป็นจำนวนเต็มบวก
- Error State: ไม่มีข่าว → แสดงข้อความ "ยังไม่มีประกาศ"; query ผิดรูปแบบ → ใช้ค่าเริ่มต้น
- Audit: ไม่บันทึก (read-only, ไม่ใช่ข้อมูลสำคัญ)
- Acceptance Criteria: AC1 เห็นเฉพาะข่าวที่เผยแพร่แล้วเท่านั้น; AC2 การแบ่งหน้าทำงานถูกต้องเมื่อข่าวเกิน 1 หน้า

**F1.2 — ดูรายละเอียดข่าว**
- Actor: Guest
- Input: slug ของข่าว
- Process: ค้นหาข่าวจาก slug, ตรวจสถานะเผยแพร่
- Output: เนื้อหาข่าวฉบับเต็ม
- Permission: ทุกคน (Public) เฉพาะข่าวที่เผยแพร่แล้ว
- Validation: slug ต้องมีอยู่จริงและสถานะ = เผยแพร่แล้ว
- Error State: ไม่พบ/ยังไม่เผยแพร่ → 404 (ไม่เปิดเผยว่ามี draft อยู่)
- Audit: ไม่บันทึก
- Acceptance Criteria: AC1 เข้าถึงข่าว draft ผ่าน URL ตรงไม่ได้แม้รู้ slug

**F1.3 — สร้าง/แก้ไขข่าว**
- Actor: Central Officer, Super Admin
- Input: หัวข้อ, เนื้อหา, ภาพปก, หมวดหมู่, สถานะ (draft/เผยแพร่)
- Process: บันทึกฉบับร่าง → ผ่านการตรวจสอบ validation → บันทึกลงฐานข้อมูลพร้อม audit record
- Output: ข่าวที่บันทึก (draft หรือเผยแพร่แล้ว)
- Permission: Central Officer, Super Admin เท่านั้น (ตรวจฝั่ง server)
- Validation: หัวข้อ/เนื้อหาไม่ว่าง, ขนาดภาพไม่เกินที่กำหนด
- Error State: บันทึกล้มเหลว → ไม่มีข้อมูลค้างสถานะไม่สมบูรณ์ (ใช้ transaction), แจ้ง error ชัดเจน
- Audit: บันทึกผู้แก้ไข, เวลา, ค่าก่อน-หลังทุกครั้ง (ตาม `data-policy.md` ข้อ 7)
- Acceptance Criteria: AC1 ผู้ใช้นอกบทบาทที่กำหนดถูกปฏิเสธฝั่ง server; AC2 ทุกการแก้ไขมี audit record ย้อนดูได้

**F1.4 — เผยแพร่/ถอดข่าว**
- Actor: Central Officer, Super Admin
- Input: newsId, สถานะใหม่ (เผยแพร่/ถอด)
- Process: เปลี่ยนสถานะ พร้อมบันทึก audit
- Output: สถานะข่าวอัปเดต
- Permission: Central Officer, Super Admin เท่านั้น
- Validation: newsId ต้องมีอยู่จริง
- Error State: newsId ไม่พบ → error 404 พร้อมข้อความชัดเจน
- Audit: บันทึกการเปลี่ยนสถานะทุกครั้ง (ผู้กระทำ, เวลา, สถานะก่อน-หลัง)
- Acceptance Criteria: AC1 ข่าวที่ถอดแล้วหายจาก `/news` ทันทีแต่ยังคงประวัติไว้ใน audit log

## Flow 2 — หลักสูตร (Curriculum)

### 2.1 ภาพรวม
1. Guest เข้า `/curriculum` → เลือกสาย (นักธรรม/ธรรมศึกษา/บาลี) → ดูรายละเอียดระดับชั้นที่ `/curriculum/[track]`
2. Guest/Member ดูตารางสอบที่ `/exam-schedule`
3. Central Officer จัดการข้อมูลอ้างอิงหลักสูตร/ระดับชั้น/สนามสอบที่ `/admin/reference-data`
4. เส้นทางผิดพลาด: track ไม่ถูกต้อง → 404; แก้ไขข้อมูลอ้างอิงที่มีการอ้างอิงใช้งานอยู่ (เช่น มีรอบสอบผูกอยู่) → ต้องยืนยันผลกระทบก่อนบันทึก

### 2.2 ฟีเจอร์

**F2.1 — ดูรายละเอียดหลักสูตร/ระดับชั้น**
- Actor: Guest
- Input: track (นักธรรม/ธรรมศึกษา/บาลี)
- Process: ดึงข้อมูลระดับชั้นและเกณฑ์ของสายที่เลือก
- Output: รายละเอียดระดับชั้น (เช่น ตรี/โท/เอก หรือ ประโยค 1–9), เกณฑ์การสอบ
- Permission: ทุกคน (Public)
- Validation: track ต้องเป็นค่าที่กำหนดไว้ล่วงหน้า
- Error State: track ไม่ถูกต้อง → 404
- Audit: ไม่บันทึก
- Acceptance Criteria: AC1 ข้อมูลที่แสดงตรงกับข้อมูลอ้างอิงล่าสุดที่ Central Officer บันทึกไว้

**F2.2 — ดูตารางสอบ/สนามสอบ**
- Actor: Guest, Member
- Input: ตัวกรอง (สาย, ระดับชั้น, ช่วงเวลา — ทั้งหมด optional)
- Process: ดึงรอบสอบที่ประกาศแล้วตามตัวกรอง
- Output: รายการรอบสอบ (วันที่, สนามสอบ, ระดับชั้น)
- Permission: ทุกคน (Public) — ไม่มีข้อมูลบุคคลในหน้านี้
- Validation: ช่วงเวลาที่กรอกต้องเป็นวันที่ถูกต้อง
- Error State: ไม่มีรอบสอบตรงเงื่อนไข → แสดงข้อความว่าง ไม่ error
- Audit: ไม่บันทึก
- Acceptance Criteria: AC1 แสดงเฉพาะรอบสอบที่ประกาศ (ไม่ใช่ draft)

**F2.3 — จัดการข้อมูลอ้างอิงหลักสูตร/ระดับชั้น/สนามสอบ**
- Actor: Central Officer, Super Admin
- Input: ข้อมูลระดับชั้น/สนามสอบ (เพิ่ม/แก้ไข/ปิดใช้งาน)
- Process: ตรวจสอบว่ามีข้อมูลอื่นอ้างอิงอยู่หรือไม่ (เช่น รอบสอบที่ผูกกับระดับชั้นนี้) → หากมี ต้องยืนยันผลกระทบก่อนบันทึก → บันทึกพร้อม audit
- Output: ข้อมูลอ้างอิงที่อัปเดต
- Permission: Central Officer, Super Admin เท่านั้น
- Validation: ห้ามลบระดับชั้นที่มีข้อมูลนักเรียน/ผลสอบผูกอยู่ (ใช้ soft-disable แทน hard delete ตาม `data-policy.md` ข้อ 7)
- Error State: พยายามลบข้อมูลที่ถูกอ้างอิงอยู่ → ปฏิเสธพร้อมระบุรายการที่อ้างอิงอยู่
- Audit: บันทึกทุกการเปลี่ยนแปลงพร้อมค่าก่อน-หลัง
- Acceptance Criteria: AC1 ข้อมูลอ้างอิงที่ถูกใช้งานอยู่ไม่สามารถลบถาวรได้; AC2 การเปลี่ยนแปลงสะท้อนใน F2.1/F2.2 ทันที

## Flow 3 — ข้อสอบ / Quiz

### 3.1 ภาพรวม
1. **แบบฝึกหัด:** Student เข้า `/my/quiz` → เลือกระดับชั้น → เริ่มทำ Quiz → ส่งคำตอบ → เห็นผลทันที (ปรนัย) หรือรอตรวจ (อัตนัย)
2. **สอบจริง:** Student เข้า `/my/exams` → สมัครสอบ → Central Officer สร้างชุดข้อสอบจากคลัง (`/admin/exam-sets`) → ถึงวันสอบ Examiner คุมสอบ → บันทึกคะแนนที่ `/examine/sessions/[id]/scores` → Central Officer ประกาศผลที่ `/admin/exam-sets` → Student เห็นผลที่ `/my/results`
3. **คลังข้อสอบ:** Teacher เสนอข้อสอบที่ `/teach/questions` → เข้า workflow อนุมัติ → Central Officer อนุมัติเข้าคลังที่ `/admin/question-bank`
4. เส้นทางผิดพลาด: สมัครสอบซ้ำ → ปฏิเสธพร้อมแจ้งสถานะเดิม; บันทึกคะแนนเกินช่วงเวลาที่อนุญาต → ต้องขออนุมัติพิเศษพร้อม audit เหตุผล; ตรวจพบข้อสอบซ้ำในคลัง → ระบบเตือนก่อนอนุมัติ

### 3.2 ฟีเจอร์

**F3.1 — ทำแบบฝึกหัด/Quiz ออนไลน์**
- Actor: Student
- Input: ระดับชั้นที่ต้องการฝึก, คำตอบของผู้ใช้
- Process: สุ่ม/เลือกชุดคำถามจากคลังข้อสอบที่เปิดให้ฝึก → บันทึกคำตอบ → ตรวจให้คะแนนอัตโนมัติ (เฉพาะปรนัย)
- Output: คะแนน + เฉลย (ตามนโยบายที่กำหนด — อาจซ่อนเฉลยจนครบเวลา)
- Permission: Student เจ้าของบัญชีเท่านั้น เข้าถึงผลของตนเอง
- Validation: ต้องตอบครบตามเงื่อนไขก่อนส่ง (ถ้ากำหนด), ห้ามส่งซ้ำหลังหมดเวลา
- Error State: หมดเวลาระหว่างทำ → บันทึกคำตอบที่มีอยู่อัตโนมัติ ไม่ให้ข้อมูลหาย; เชื่อมต่อขาดหาย → กู้คืนคำตอบที่บันทึกล่าสุดได้
- Audit: บันทึกการทำ Quiz แต่ละครั้ง (ไม่ต้องละเอียดเท่าการสอบจริง แต่ต้องสืบย้อนได้ว่าใครทำเมื่อใด)
- Acceptance Criteria: AC1 คะแนนปรนัยคำนวณถูกต้อง 100% เทียบกับเฉลย; AC2 ผู้ใช้เห็นเฉพาะผลของตนเอง

**F3.2 — สมัครสอบ**
- Actor: Student
- Input: รอบสอบที่ต้องการสมัคร
- Process: ตรวจสอบคุณสมบัติ (ระดับชั้นก่อนหน้าผ่านหรือไม่ ถ้ากำหนดเป็นเงื่อนไข) → ตรวจสอบว่าสมัครซ้ำหรือไม่ → บันทึกการสมัครภายใน transaction
- Output: สถานะการสมัคร (ยืนยันแล้ว/รอดำเนินการ)
- Permission: Student เจ้าของบัญชีเท่านั้น สมัครแทนผู้อื่นไม่ได้ (ยกเว้น Registrar Staff สมัครแทนในสังกัดตน — เป็นฟีเจอร์แยก จะระบุในเฟสพัฒนา M4)
- Validation: ไม่สมัครซ้ำรอบเดียวกัน, ต้องอยู่ในช่วงเวลาเปิดรับสมัคร
- Error State: สมัครซ้ำ → ปฏิเสธพร้อมแจ้งสถานะเดิม; รอบสอบปิดรับสมัครแล้ว → ปฏิเสธพร้อมแจ้งเหตุผล
- Audit: บันทึกทุกการสมัคร/ยกเลิกพร้อมเวลา
- Acceptance Criteria: AC1 ไม่มีการสมัครซ้ำเกิดขึ้นได้แม้ยิง request พร้อมกัน (race condition ป้องกันด้วย transaction/unique constraint)

**F3.3 — เสนอ/ทบทวนข้อสอบเข้าคลัง**
- Actor: Teacher
- Input: ข้อสอบ (คำถาม, ตัวเลือก/เฉลย, ระดับชั้น, หมวดหมู่)
- Process: บันทึกเป็นสถานะ "รอตรวจทาน" → เข้า workflow อนุมัติของ Central Officer
- Output: ข้อสอบสถานะรอตรวจทาน
- Permission: Teacher เสนอได้เฉพาะระดับชั้น/วิชาที่ตนได้รับมอบหมาย
- Validation: ฟิลด์บังคับครบ (คำถาม, เฉลยอย่างน้อย 1 ข้อ)
- Error State: บันทึกไม่สำเร็จ → ไม่มีข้อมูลค้างสถานะไม่สมบูรณ์
- Audit: บันทึกผู้เสนอ, เวลา, เวอร์ชันของข้อสอบ (ตาม `data-policy.md` ข้อ 7 — ห้ามเขียนทับเวอร์ชันเดิม)
- Acceptance Criteria: AC1 ข้อสอบที่เสนอไม่ปรากฏในคลังใช้งานจริงจนกว่าจะได้รับอนุมัติ

**F3.4 — สร้างชุดข้อสอบจากคลัง**
- Actor: Central Officer
- Input: เกณฑ์การเลือกข้อสอบ (ระดับชั้น, จำนวนข้อ, หมวดหมู่) หรือเลือกเอง
- Process: ดึงข้อสอบที่สถานะอนุมัติแล้วตามเกณฑ์ → ประกอบเป็นชุด → ผูกกับรอบสอบ
- Output: ชุดข้อสอบพร้อมใช้งาน ผูกกับรอบสอบที่ระบุ
- Permission: Central Officer, Super Admin เท่านั้น
- Validation: ใช้ได้เฉพาะข้อสอบสถานะอนุมัติแล้ว
- Error State: ข้อสอบไม่พอตามเกณฑ์ → แจ้งเตือนก่อนยืนยัน ไม่สร้างชุดที่ไม่ครบ
- Audit: บันทึกผู้สร้างชุด, องค์ประกอบของชุด, เวลา
- Acceptance Criteria: AC1 ชุดข้อสอบที่สร้างมีเฉพาะข้อที่อนุมัติแล้วเท่านั้น

**F3.5 — บันทึกคะแนน/ตรวจข้อสอบ (สอบจริง)**
- Actor: Examiner
- Input: sessionId, คะแนนต่อผู้เข้าสอบ
- Process: ตรวจสอบว่า Examiner ได้รับมอบหมายรอบสอบนี้จริง → บันทึกคะแนนภายใน transaction พร้อม audit
- Output: คะแนนที่บันทึก (ยังไม่เผยแพร่ให้ Student จนกว่า Central Officer ประกาศผล)
- Permission: Examiner ที่ได้รับมอบหมายรอบสอบนั้นเท่านั้น
- Validation: คะแนนต้องอยู่ในช่วงที่กำหนด (เช่น 0–100), ผู้เข้าสอบต้องมีอยู่ในรอบสอบนั้นจริง
- Error State: แก้ไขคะแนนหลังปิดรอบตรวจ → ต้องผ่านการอนุมัติพิเศษพร้อมระบุเหตุผล (บันทึก audit เพิ่มเติม ไม่ใช่แก้ทับเงียบ ๆ)
- Audit: บันทึกทุกการบันทึก/แก้ไขคะแนน พร้อมผู้กระทำ, เวลา, ค่าก่อน-หลัง
- Acceptance Criteria: AC1 Examiner นอกรอบที่ได้รับมอบหมายถูกปฏิเสธฝั่ง server; AC2 การแก้ไขคะแนนทุกครั้งมี audit ที่สืบย้อนได้

**F3.6 — ประกาศผลสอบ**
- Actor: Central Officer, Super Admin
- Input: sessionId/examSetId ที่ต้องการประกาศ
- Process: ตรวจสอบว่าคะแนนครบทุกผู้เข้าสอบในรอบนั้น → เปลี่ยนสถานะเป็น "ประกาศผลแล้ว" → เปิดให้ Student เห็นผลของตนเอง
- Output: สถานะรอบสอบ = ประกาศผลแล้ว
- Permission: Central Officer, Super Admin เท่านั้น
- Validation: คะแนนต้องครบทุกคนก่อนประกาศ (หรือมีเหตุผลชัดเจนหากประกาศบางส่วน)
- Error State: คะแนนไม่ครบ → ปฏิเสธการประกาศ พร้อมแจ้งรายชื่อ/จำนวนที่ยังไม่ครบ
- Audit: บันทึกผู้ประกาศ, เวลา, ขอบเขตที่ประกาศ
- Acceptance Criteria: AC1 Student เห็นผลได้ก็ต่อเมื่อสถานะ = ประกาศผลแล้วเท่านั้น

## Flow 4 — เอกสาร (Documents)

### 4.1 ภาพรวม
1. Registrar Staff/Central Officer อัปโหลดเอกสารแนบที่ `/registry/documents` หรือ `/admin/*`
2. ระบบ (System Job) หรือ Central Officer ออกใบประกาศนียบัตร PDF หลังประกาศผลสอบผ่านเกณฑ์
3. Student ดาวน์โหลดเอกสาร/ใบประกาศนียบัตรของตนเองที่ `/my/documents`
4. เส้นทางผิดพลาด: ไฟล์เกินขนาด/ผิดชนิด → ปฏิเสธก่อนอัปโหลดจริง; พยายามเข้าถึงไฟล์นอกสิทธิ์ → ปฏิเสธฝั่ง server แม้ทราบ URL ตรง (ไม่ใช้ public URL แบบเดาได้)

### 4.2 ฟีเจอร์

**F4.1 — อัปโหลดเอกสารแนบ**
- Actor: Registrar Staff, Central Officer, Super Admin
- Input: ไฟล์ (PDF/รูปภาพตามชนิดที่กำหนด), ประเภทเอกสาร, entity ที่ผูก (เช่น ทะเบียนบุคคล)
- Process: ตรวจชนิด/ขนาดไฟล์ → อัปโหลดเข้า Object Storage (bucket/prefix ตาม environment ตาม `data-policy.md` ข้อ 8) → บันทึก metadata + สิทธิ์เข้าถึงในฐานข้อมูล
- Output: เอกสารที่ผูกกับ entity พร้อม metadata
- Permission: เฉพาะผู้มีสิทธิ์แก้ไข entity ที่ผูกอยู่ (ตาม scope สังกัด/เขต)
- Validation: ชนิดไฟล์อยู่ใน whitelist, ขนาดไม่เกินที่กำหนด, สแกนไวรัส/มัลแวร์เบื้องต้น (ถ้ามีเครื่องมือรองรับ)
- Error State: ไฟล์ผิดชนิด/เกินขนาด/สแกนไม่ผ่าน → ปฏิเสธก่อนบันทึก พร้อมข้อความชัดเจน; อัปโหลดสำเร็จแต่บันทึก metadata ล้มเหลว → ลบไฟล์ที่อัปโหลดค้างออกจาก storage (ไม่ปล่อยไฟล์กำพร้า)
- Audit: บันทึกผู้อัปโหลด, เวลา, entity ที่ผูก, ชื่อไฟล์ (ไม่บันทึกเนื้อหาไฟล์ใน audit log)
- Acceptance Criteria: AC1 ไฟล์ที่อัปโหลดเข้าถึงได้เฉพาะผู้มีสิทธิ์ตาม entity ที่ผูก; AC2 ไม่มีไฟล์กำพร้าค้างใน storage เมื่อบันทึก metadata ล้มเหลว

**F4.2 — ดาวน์โหลดเอกสารของตนเอง**
- Actor: Student (เอกสารของตนเอง), Registrar Staff/Regional Admin (เอกสารในสังกัด/เขตตน)
- Input: documentId
- Process: ตรวจสิทธิ์เข้าถึง entity ที่เอกสารผูกอยู่ฝั่ง server → สร้าง signed URL ชั่วคราวหรือ stream ไฟล์ผ่าน server
- Output: ไฟล์เอกสาร
- Permission: ตาม scope ของ Actor (deny-by-default หากไม่ตรง scope)
- Validation: documentId ต้องมีอยู่จริงและผูกกับ entity ที่ผู้ใช้มีสิทธิ์
- Error State: ไม่มีสิทธิ์ → 403; ไฟล์ไม่พบใน storage (ข้อมูลไม่สอดคล้อง) → แจ้ง error และบันทึก log สำหรับตรวจสอบ
- Audit: บันทึกการเข้าถึง/ดาวน์โหลดเอกสาร Restricted ทุกครั้ง (ผู้ดู, เวลา)
- Acceptance Criteria: AC1 ไม่สามารถดาวน์โหลดเอกสารของผู้อื่นได้แม้เดา URL/ID ถูก

**F4.3 — ออกใบประกาศนียบัตร (PDF)**
- Actor: Central Officer, Super Admin (สั่งการ), System Job (ประมวลผลจริง)
- Input: sessionId/รายชื่อผู้สอบผ่านเกณฑ์
- Process: ตรวจสอบว่าผลสอบ = ประกาศผลแล้วและผ่านเกณฑ์ → สร้างไฟล์ PDF จาก template → บันทึกเข้า Object Storage → ผูกกับทะเบียนบุคคลนั้น
- Output: ไฟล์ใบประกาศนียบัตรต่อผู้สอบผ่าน
- Permission: สั่งการได้เฉพาะ Central Officer/Super Admin; ตัวกระบวนการสร้างไฟล์ทำงานภายใต้ System Job service account
- Validation: ออกได้เฉพาะผู้ที่ผลสอบ = ผ่านเกณฑ์และประกาศผลแล้วเท่านั้น
- Error State: สร้าง PDF บางส่วนล้มเหลว (เช่น ไฟล์ที่ 50 จาก 100 ล้มเหลว) → รายงานรายชื่อที่ล้มเหลวแยกจากที่สำเร็จ ไม่ต้องยกเลิกทั้งชุด แต่ต้องสามารถสั่งสร้างซ้ำเฉพาะรายที่ล้มเหลวได้ (idempotent)
- Audit: บันทึกผู้สั่งออกใบประกาศ, เวลา, รายชื่อที่สำเร็จ/ล้มเหลว
- Acceptance Criteria: AC1 ไม่ออกใบประกาศให้ผู้ที่ไม่ผ่านเกณฑ์; AC2 สั่งสร้างซ้ำเฉพาะรายที่ล้มเหลวได้โดยไม่สร้างไฟล์ซ้ำซ้อนสำหรับรายที่สำเร็จแล้ว

## Flow 5 — สมัครสมาชิก (Registration)

### 5.1 ภาพรวม
1. Guest เข้า `/register` → กรอกข้อมูล → ยืนยันอีเมล → (ถ้าบทบาทต้องอนุมัติ เช่น Registrar Staff/Regional Admin) รออนุมัติจากผู้มีสิทธิ์ → เข้าสู่ระบบครั้งแรกที่ `/login`
2. เส้นทางผิดพลาด: อีเมลซ้ำ → แจ้งทันทีที่ฟอร์ม; ไม่ยืนยันอีเมลภายในเวลาที่กำหนด → บัญชีค้างสถานะรอยืนยัน ไม่ auto-activate

### 5.2 ฟีเจอร์

**F5.1 — กรอกแบบฟอร์มสมัครสมาชิก**
- Actor: Guest
- Input: อีเมล, รหัสผ่าน, ข้อมูลพื้นฐาน (ชื่อ-นามสกุล, บทบาทที่ขอสมัคร ถ้าเลือกได้), การยอมรับข้อกำหนดการใช้งาน
- Process: ตรวจสอบ validation → ตรวจอีเมลซ้ำ → สร้างบัญชีสถานะ "รอยืนยันอีเมล" → ส่งอีเมลยืนยัน
- Output: บัญชีสถานะรอยืนยัน + อีเมลยืนยันถูกส่ง
- Permission: ทุกคน (Public) — สมัครเป็น Student ได้เอง; บทบาทระดับสูงกว่า (Registrar Staff ขึ้นไป) สร้างโดย Admin เท่านั้น ไม่เปิดให้สมัครเองผ่านฟอร์มนี้
- Validation: อีเมลรูปแบบถูกต้องและไม่ซ้ำ, รหัสผ่านตามนโยบายความปลอดภัยขั้นต่ำ, ต้องยอมรับข้อกำหนดการใช้งาน
- Error State: อีเมลซ้ำ → แจ้งข้อความทั่วไป (ไม่ยืนยัน/ปฏิเสธชัดว่ามีบัญชีอยู่แล้วเพื่อป้องกัน account enumeration ตามความเหมาะสม — รายละเอียดสุดท้ายกำหนดในการออกแบบ security ที่ P2); รหัสผ่านไม่ผ่านเกณฑ์ → แจ้งเงื่อนไขที่ขาด
- Audit: บันทึกการสมัครสมาชิกทุกครั้ง (เวลา, อีเมล — เป็นข้อมูล Restricted ต้องจัดการตาม `data-policy.md`)
- Acceptance Criteria: AC1 ไม่มีบัญชีซ้ำอีเมลเดียวกันเกิดขึ้นได้แม้สมัครพร้อมกัน (unique constraint ระดับฐานข้อมูล)

**F5.2 — ยืนยันอีเมล**
- Actor: Guest (เจ้าของบัญชีที่เพิ่งสมัคร)
- Input: token ยืนยันจากอีเมล
- Process: ตรวจสอบ token ถูกต้องและยังไม่หมดอายุ → เปลี่ยนสถานะบัญชีเป็น "ยืนยันแล้ว" (หรือ "รออนุมัติ" ถ้าบทบาทต้องอนุมัติ)
- Output: สถานะบัญชีอัปเดต
- Permission: เจ้าของ token เท่านั้น
- Validation: token ต้องไม่หมดอายุและยังไม่ถูกใช้
- Error State: token หมดอายุ/ใช้ไปแล้ว → แจ้งให้ขอส่งใหม่
- Audit: บันทึกเวลาที่ยืนยันสำเร็จ
- Acceptance Criteria: AC1 token ใช้ได้ครั้งเดียว; AC2 บัญชีที่ไม่ยืนยันภายในเวลาที่กำหนดไม่สามารถล็อกอินได้

**F5.3 — อนุมัติบัญชี (เฉพาะบทบาทที่ต้องอนุมัติ)**
- Actor: Regional Admin (อนุมัติ Registrar Staff ในเขต), Super Admin (อนุมัติบทบาทระดับสูง)
- Input: userId ที่รออนุมัติ, การตัดสินใจ (อนุมัติ/ปฏิเสธ), เหตุผล (กรณีปฏิเสธ)
- Process: ตรวจสอบสิทธิ์ผู้อนุมัติตรงกับ scope ของผู้ขอ → เปลี่ยนสถานะบัญชี → แจ้งผู้สมัครผ่านอีเมล
- Output: บัญชีสถานะ "ใช้งานได้" หรือ "ถูกปฏิเสธ"
- Permission: เฉพาะผู้มีสิทธิ์อนุมัติในขอบเขตที่เกี่ยวข้อง (deny-by-default หากอยู่นอกเขต)
- Validation: userId ต้องอยู่ในสถานะ "รออนุมัติ" เท่านั้นจึงจะดำเนินการได้
- Error State: อนุมัติซ้ำ/บัญชีถูกดำเนินการไปแล้ว → ปฏิเสธพร้อมแจ้งสถานะปัจจุบัน
- Audit: บันทึกผู้อนุมัติ/ปฏิเสธ, เวลา, เหตุผล (ถ้ามี)
- Acceptance Criteria: AC1 บัญชีที่ยังไม่อนุมัติล็อกอินเข้าใช้งานจริงไม่ได้; AC2 ผู้อนุมัตินอกขอบเขตถูกปฏิเสธฝั่ง server

**F5.4 — เข้าสู่ระบบครั้งแรก**
- Actor: Member ที่บัญชีสถานะ "ใช้งานได้"
- Input: email, password
- Process: เหมือน Login มาตรฐาน (อ้างอิงสเปกฉบับยาวใน `requirements.md` ข้อ 8) แต่เพิ่มการตรวจสถานะบัญชี "ใช้งานได้" ก่อนอนุญาต
- Output: session + redirect เข้า `/dashboard`
- Permission: เฉพาะบัญชีสถานะ "ใช้งานได้"
- Validation: อีเมล/รหัสผ่านถูกต้อง และสถานะบัญชีต้องเป็น "ใช้งานได้"
- Error State: บัญชียังไม่ยืนยัน/รออนุมัติ/ถูกปฏิเสธ → แจ้งสถานะที่ชัดเจนพร้อมขั้นตอนถัดไป
- Audit: บันทึกการล็อกอินสำเร็จ/ล้มเหลว (เหมือน Login มาตรฐาน)
- Acceptance Criteria: AC1 บัญชีที่ยังไม่ผ่านทุกขั้นตอน (ยืนยันอีเมล/อนุมัติ) ล็อกอินไม่สำเร็จพร้อมข้อความอธิบายสถานะ

## Flow 6 — หลังบ้าน (Admin / Back Office)

### 6.1 ภาพรวม
1. Super Admin เข้า `/admin/users` และ `/admin/roles` → บริหารผู้ใช้/บทบาททั้งระบบ
2. Central Officer เข้า `/admin/reference-data`, `/admin/import` → บริหารข้อมูลอ้างอิงและนำเข้าข้อมูลระดับศูนย์กลาง
3. Auditor/Super Admin เข้า `/admin/audit-log` → ตรวจสอบประวัติการเปลี่ยนแปลง
4. Super Admin เข้า `/admin/settings` → ตั้งค่าระบบ
5. เส้นทางผิดพลาด: พยายามลดสิทธิ์ตัวเองจนไม่มี Super Admin เหลือในระบบ → ปฏิเสธ (ป้องกัน lockout); นำเข้าข้อมูลศูนย์กลางผิดพลาดบางส่วน → ใช้กระบวนการเดียวกับ F ตัวอย่าง Excel Import ใน `requirements.md` ข้อ 8

### 6.2 ฟีเจอร์

**F6.1 — จัดการผู้ใช้และบทบาท**
- Actor: Super Admin
- Input: userId, การเปลี่ยนแปลง (บทบาท, สถานะบัญชี, scope)
- Process: ตรวจสอบว่าการเปลี่ยนแปลงจะไม่ทำให้ระบบไม่มี Super Admin เหลือเลย → บันทึกการเปลี่ยนแปลงพร้อม audit
- Output: ข้อมูลผู้ใช้ที่อัปเดต
- Permission: Super Admin เท่านั้น
- Validation: ต้องมี Super Admin อย่างน้อย 1 บัญชีที่ใช้งานได้เสมอในระบบ
- Error State: การเปลี่ยนแปลงจะทำให้ไม่มี Super Admin เหลือ → ปฏิเสธพร้อมคำอธิบาย
- Audit: บันทึกทุกการเปลี่ยนแปลงบทบาท/สถานะผู้ใช้ พร้อมค่าก่อน-หลัง
- Acceptance Criteria: AC1 ระบบไม่มีวันเหลือ Super Admin เป็น 0 บัญชี; AC2 ทุกการเปลี่ยนแปลงสิทธิ์มี audit ที่สืบย้อนได้

**F6.2 — จัดการข้อมูลอ้างอิง (Master Data)**
- Actor: Central Officer, Super Admin
- Process/รายละเอียด: เช่นเดียวกับ F2.3 (จัดการข้อมูลอ้างอิงหลักสูตร) และขยายครอบคลุมโครงสร้างการปกครอง (ภาค/จังหวัด/อำเภอ/ตำบล)
- Input: ข้อมูลโครงสร้างการปกครอง/ข้อมูลอ้างอิงอื่น ๆ
- Output: ข้อมูลอ้างอิงที่อัปเดต
- Permission: Central Officer, Super Admin เท่านั้น
- Validation: เหมือน F2.3 — ห้ามลบข้อมูลที่ถูกอ้างอิงใช้งานอยู่
- Error State: เหมือน F2.3
- Audit: บันทึกทุกการเปลี่ยนแปลง
- Acceptance Criteria: AC1 การเปลี่ยนโครงสร้างการปกครองไม่ทำให้ทะเบียนที่ผูกอยู่ชี้ไปยังเขตที่ไม่มีอยู่จริง (referential integrity)

**F6.3 — นำเข้าข้อมูล Excel ระดับศูนย์กลาง**
- Actor: Central Officer, Super Admin
- Input: ไฟล์ .xlsx ตาม template กลาง (เหมือนตัวอย่างที่ 2 ใน `requirements.md` ข้อ 8 แต่ไม่จำกัด scope สังกัดเดียว)
- Process: เหมือนตัวอย่างที่ 2 ใน `requirements.md` ข้อ 8 ทุกขั้นตอน (dry-run → รายงานผล → ยืนยัน → บันทึกภายใน transaction) ต่างกันที่ scope ครอบคลุมข้ามสังกัด/ข้ามเขตได้เพราะเป็นระดับศูนย์กลาง
- Output: รายงานผลการนำเข้า (สำเร็จ/ล้มเหลว/รายละเอียดต่อแถว) เหมือนตัวอย่างเดิม
- Permission: Central Officer, Super Admin เท่านั้น (ต่างจาก Registrar Staff ที่จำกัด scope เฉพาะสังกัดตนในหน้า `/registry/import`)
- Validation: เหมือนตัวอย่างที่ 2 ใน `requirements.md` ข้อ 8 (เลขทะเบียนไม่ซ้ำ, ข้อมูลอ้างอิงต้องมีอยู่จริง, ฟิลด์บังคับครบ)
- Error State: เหมือนตัวอย่างที่ 2 (ไฟล์ผิดรูปแบบ, แถวผิดพลาดบางส่วน, ระบบขัดข้องระหว่างบันทึก → rollback)
- Audit: บันทึกผู้ทำรายการ, เวลา, ไฟล์ต้นฉบับ, ขอบเขตสังกัด/เขตที่ครอบคลุม, จำนวนแถวสำเร็จ/ล้มเหลว
- Acceptance Criteria: AC1–AC4 เหมือนตัวอย่างใน `requirements.md` ข้อ 8 เพิ่มเติม AC5: ผู้ใช้ที่ไม่ใช่ Central Officer/Super Admin ถูกปฏิเสธฝั่ง server แม้พยายามเรียก endpoint นี้ตรง ๆ

**F6.4 — ดู Audit Log**
- Actor: Auditor, Super Admin
- Input: ตัวกรอง (ช่วงเวลา, entity type, ผู้กระทำ)
- Process: ดึง audit record ตามตัวกรอง (read-only, ไม่มีการแก้ไข)
- Output: รายการ audit record
- Permission: Auditor (อ่านอย่างเดียว), Super Admin
- Validation: ช่วงเวลาที่กรองต้องถูกต้อง
- Error State: ไม่มีข้อมูลตรงเงื่อนไข → แสดงว่าง
- Audit: การเข้าดู audit log เองไม่จำเป็นต้องสร้าง audit ซ้อน เว้นแต่ต้องการ compliance ระดับสูง (กำหนดในเฟส P2)
- Acceptance Criteria: AC1 Auditor แก้ไข/ลบ audit record ไม่ได้แม้พยายามผ่าน API โดยตรง

**F6.5 — ตั้งค่าระบบ**
- Actor: Super Admin
- Input: ค่าคอนฟิก (เช่น นโยบายรหัสผ่าน, session timeout, จำนวนครั้งที่ล็อกอินผิดก่อนล็อกบัญชี)
- Process: ตรวจสอบค่าที่กรอกอยู่ในช่วงที่ยอมรับได้ → บันทึกและมีผลทันที/ตามรอบที่กำหนด
- Output: ค่าคอนฟิกที่อัปเดต
- Permission: Super Admin เท่านั้น
- Validation: ค่าต้องอยู่ในช่วงที่กำหนดไว้ล่วงหน้า (เช่น session timeout ไม่ต่ำกว่า/สูงกว่าที่กำหนด)
- Error State: ค่าผิดช่วง → ปฏิเสธพร้อมแจ้งช่วงที่ยอมรับได้
- Audit: บันทึกทุกการเปลี่ยนค่าคอนฟิกพร้อมค่าก่อน-หลัง
- Acceptance Criteria: AC1 ค่าคอนฟิกที่ผิดช่วงไม่สามารถบันทึกได้; AC2 การเปลี่ยนแปลงมีผลตามที่ระบุและมี audit
