# Requirements Specification

**โครงการ:** ระบบฐานข้อมูลคณะสงฆ์และการศึกษาพระปริยัติธรรม (นักธรรม / ธรรมศึกษา / บาลี) พร้อมคลังข้อสอบ ระบบแบบทดสอบ ระบบสมาชิก และระบบผู้ดูแลระบบ
**เฟส:** P0 — Orientation & Safety
**อ้างอิงคู่กับ:** `project-charter.md`
**สถานะ:** ร่างสำหรับ Owner Review
**เวอร์ชัน:** 0.1 | **วันที่:** 2026-09-14

> ข้อมูลทั้งหมดในเอกสารนี้เป็น**ข้อมูลสมมติ**เพื่อการอธิบายเท่านั้น ไม่มีชื่อบุคคล วัด หรือหน่วยงานจริง

---

## 1. วัตถุประสงค์และขอบเขตเอกสาร

เอกสารนี้กำหนดความต้องการของระบบในระดับที่เพียงพอสำหรับเริ่มออกแบบสถาปัตยกรรมและวางแผนเฟสถัดไป (P1 เป็นต้นไป) โดยละเอียดของแต่ละโมดูล (full function spec ครบทุกฟังก์ชัน) จะจัดทำเป็นเอกสารย่อยต่อโมดูลในเฟสที่โมดูลนั้นเริ่มพัฒนา ตามรูปแบบ (template) ที่กำหนดไว้ในหัวข้อ 8

## 2. เทคโนโลยีอ้างอิง

Next.js (App Router) · TypeScript · Tailwind CSS · shadcn/ui · PostgreSQL · Prisma · Auth.js

## 3. Actors — นิยามและสิทธิ์โดยสังเขป

| Actor | นิยาม | ขอบเขตข้อมูลที่เข้าถึง |
|---|---|---|
| **Super Admin** | ผู้ดูแลระบบสูงสุดขององค์กร | ทั้งระบบ ทุกเขตปกครอง ทุกโมดูล |
| **เจ้าหน้าที่ส่วนกลาง (Central Officer)** | เจ้าหน้าที่สำนักงานส่วนกลางที่ดูแลข้อมูลอ้างอิงและคลังข้อสอบ | ทั้งระบบ (ยกเว้นการตั้งค่าระบบระดับ Super Admin) |
| **ผู้บริหารคณะสงฆ์ระดับภาค/จังหวัด/อำเภอ/ตำบล (Regional Admin)** | ผู้มีอำนาจปกครองตามลำดับชั้นในเขตของตน | เฉพาะข้อมูลในเขตปกครองของตนและเขตย่อยที่อยู่ใต้บังคับบัญชา |
| **เจ้าหน้าที่ธุรการสำนักเรียน/วัด (Registrar Staff)** | บันทึก/ปรับปรุงข้อมูลระดับปฏิบัติการ | เฉพาะวัด/สำนักเรียนที่ตนสังกัด |
| **ครูสอนธรรม/ครูสอนบาลี (Teacher)** | ผู้สอนและเสนอ/ทบทวนข้อสอบ | เฉพาะข้อสอบ/นักเรียนในความรับผิดชอบของตน |
| **ผู้ตรวจข้อสอบ/กรรมการคุมสอบ (Examiner)** | บันทึกคะแนน จัดการรอบสอบ | เฉพาะรอบสอบที่ได้รับมอบหมาย |
| **นักเรียน/ผู้เข้าสอบ (Student)** | ผู้ใช้งานปลายทางที่ศึกษา/สอบ | เฉพาะข้อมูลของตนเอง |
| **ผู้ตรวจสอบภายใน (Auditor)** | ตรวจสอบความถูกต้อง/การปฏิบัติตามนโยบาย | อ่านอย่างเดียว (read-only) ทั่วทั้งระบบ รวม audit log |
| **บุคคลทั่วไป (Guest)** | ผู้เยี่ยมชมที่ไม่ได้ล็อกอิน | เฉพาะหน้าสาธารณะที่กำหนดไว้ชัดเจน (เช่น ตรวจผลสอบด้วยเลขอ้างอิง หากเปิดให้บริการ) |
| **System/Scheduled Job** | กระบวนการอัตโนมัติภายในระบบ | เฉพาะขอบเขตที่ configuration กำหนด ทำงานภายใต้ service account แยกจากผู้ใช้ |

> รายละเอียดสิทธิ์แบบตาราง (role × module × action) จะจัดทำเป็น permission matrix ฉบับสมบูรณ์ใน P2 (Auth & RBAC Foundation) โดยใช้โครงร่างในหัวข้อ 6 เป็นจุดเริ่มต้น

## 4. ขอบเขตโมดูล (Modules) — In Scope

### M1. ทะเบียนคณะสงฆ์ (Sangha Registry)
พระภิกษุ/สามเณร, วัด, สำนักเรียน, โครงสร้างสายการปกครอง (ภาค → จังหวัด → อำเภอ → ตำบล), สถานะการบวช/ลาสิกขา/ย้ายสังกัด พร้อมประวัติการเปลี่ยนแปลงทุกครั้ง

### M2. หลักสูตรและระดับการศึกษา
- นักธรรม: ตรี, โท, เอก
- ธรรมศึกษา: ตรี, โท, เอก
- บาลี: ประโยค 1–9 (ประโยค 1-2 ถึง ป.ธ.9)
- สนามสอบ, ปีการศึกษา/รอบสอบ

### M3. คลังข้อสอบ (Question Bank)
หมวดหมู่ตามระดับชั้น/รายวิชา, ชนิดข้อสอบ (ปรนัย/อัตนัย), metadata (ผู้แต่ง, วันที่, สถานะอนุมัติ), เวอร์ชัน (versioning — ห้ามลบ/เขียนทับของเดิมเมื่อมีการแก้ไข), workflow อนุมัติก่อนนำไปใช้จริง

### M4. ระบบแบบทดสอบ/จัดสอบ (Testing Engine)
สร้างชุดข้อสอบจากคลังข้อสอบ, รองรับทั้ง (ก) การสอบจริงระดับสนามสอบที่บันทึกผลย้อนหลัง และ (ข) แบบฝึกหัด/สอบจำลองออนไลน์สำหรับนักเรียน, กระบวนการตรวจให้คะแนน (อัตโนมัติสำหรับปรนัย / มีผู้ตรวจสำหรับอัตนัย), ประกาศผลพร้อมสถานะที่ตรวจสอบย้อนหลังได้

### M5. ระบบสมาชิก (Membership)
สมัครสมาชิก, ยืนยันตัวตนผ่าน Auth.js, จัดการโปรไฟล์, การกู้คืนบัญชี, การจัดการ session อย่างปลอดภัย

### M6. ผู้ดูแลระบบ (Admin Console)
จัดการผู้ใช้/บทบาท/สิทธิ์, จัดการข้อมูลอ้างอิง (master data), ตั้งค่าระบบ, หน้าจอดู audit log และรายงาน

### M7. นำเข้าข้อมูล Excel (Excel Import)
นำเข้ารายชื่อพระภิกษุ/นักเรียน/ผลสอบเป็นชุด, ตรวจสอบรูปแบบและความถูกต้องรายแถว (validation), แสดงรายงานข้อผิดพลาดก่อนยืนยัน (dry-run), การนำเข้าจริงต้องอยู่ใน transaction เดียวหรือแบ่งเป็นชุดที่ rollback ได้เมื่อผิดพลาด

### M8. จัดเก็บไฟล์ (PDF/Object Storage)
ใบประกาศนียบัตร, เอกสารแนบประกอบทะเบียน, ไฟล์ข้อสอบ PDF, ใบสมัครสอบ — ควบคุมสิทธิ์การเข้าถึงไฟล์ตาม RBAC เดียวกับข้อมูลต้นทาง ไม่เปิด public URL โดยไม่มีการตรวจสิทธิ์

### M9. สิทธิ์การเข้าถึงหลายระดับ (Multi-level RBAC)
กำหนดสิทธิ์ตามบทบาท + ลำดับชั้นการปกครอง (hierarchical scoping) เช่น ผู้บริหารระดับจังหวัดเห็นเฉพาะข้อมูลในจังหวัดตนและอำเภอ/ตำบลใต้สังกัด บังคับใช้ทุกจุดฝั่ง server, ยึด deny-by-default

## 5. ความต้องการที่ไม่ใช่เชิงหน้าที่ (Non-Functional Requirements)

| หมวด | ความต้องการ | หมายเหตุ |
|---|---|---|
| ความปลอดภัย | Authorization ตรวจสอบฝั่ง server ทุก request, deny-by-default | บังคับทุกโมดูล |
| Auditability | ทุก create/update/delete บนข้อมูลสำคัญ (ทะเบียนพระภิกษุ, ผลสอบ, สิทธิ์ผู้ใช้) บันทึก audit log พร้อมผู้กระทำ/เวลา/ค่าก่อน-หลัง | ห้าม overwrite ประวัติเดิม |
| ความถูกต้องของข้อมูล (Data Integrity) | Operation ที่ต้อง atomic ใช้ database transaction | เช่น import แบบชุด, บันทึกผลสอบพร้อมอัปเดตสถานะ |
| ความพร้อมใช้งาน (Availability) | เป้าหมายจะกำหนดตัวเลขที่วัดได้ใน P1 หลังยืนยัน hosting | Placeholder — ยังไม่ระบุ SLA |
| ประสิทธิภาพ (Performance) | เป้าหมาย response time/หน้าโหลด จะกำหนดใน P1 | Placeholder |
| การรองรับภาษา (i18n) | ภาษาไทยเป็นหลัก, ภาษาอังกฤษสำหรับป้ายกำกับทางเทคนิค (ถ้าจำเป็น) | ยืนยันขอบเขตกับ Owner |
| ความสามารถในการเข้าถึง (Accessibility) | ปฏิบัติตามแนวทางพื้นฐาน (WCAG 2.1 AA เป็นเป้าหมาย) | รายละเอียดกำหนดใน P1 |
| ความสามารถในการตรวจสอบย้อนกลับ (Traceability) | ทุก requirement ต้องเชื่อมโยงกับ acceptance criteria และ test case ในเฟสพัฒนา | ใช้ template หัวข้อ 8 |
| ความปลอดภัยของ Secrets | ห้าม commit secrets, ใช้ `.env.example` | บังคับทุก repository |

## 7. ข้อจำกัดด้านข้อมูล (Data Constraints)

1. Development/Test environment ใช้เฉพาะข้อมูลสมมติ (synthetic/fixture data) จนกว่าจะผ่าน **Real-data Readiness Gate** (นิยามใน `project-charter.md` ข้อ 9)
2. ห้ามมีข้อมูลบุคคลจริงใน seed script, screenshot, log หรือ test fixture โดยเด็ดขาด
3. Seed data ต้องระบุอย่างชัดเจนว่าเป็นข้อมูลสมมติ (เช่น prefix ชื่อ "ทดสอบ" หรือใช้ mock data generator)
4. Log ที่มีข้อมูลอ่อนไหว (เช่น เลขบัตรประชาชน หากมีในอนาคต) ต้อง mask ก่อนบันทึก
5. Object storage ของไฟล์แนบต้องแยก bucket/prefix ระหว่าง dev/test และ production อย่างชัดเจน

## 8. รูปแบบมาตรฐานการระบุฟังก์ชัน (Function Specification Template)

ทุกฟังก์ชันที่พัฒนาในเฟสถัดไปต้องระบุองค์ประกอบต่อไปนี้ครบถ้วนก่อนเริ่มพัฒนา (ใช้เป็นส่วนหนึ่งของ Definition of Ready):

```
Function: <ชื่อฟังก์ชัน>
Actor: <ผู้ใช้งาน/บทบาทที่เรียกใช้>
Input: <ข้อมูลนำเข้า พร้อมชนิดข้อมูล>
Process: <ลำดับการประมวลผลหลัก>
Output: <ผลลัพธ์ที่ส่งคืน>
Permission: <บทบาทที่มีสิทธิ์ + เงื่อนไข scope>
Validation: <กฎการตรวจสอบข้อมูลนำเข้า>
Error State: <กรณีผิดพลาดที่เป็นไปได้และการตอบสนองของระบบ>
Audit: <เหตุการณ์ที่ต้องบันทึกลง audit log>
Acceptance Criteria: <เงื่อนไขที่ถือว่าฟังก์ชันนี้ผ่านการยอมรับ>
```

### ตัวอย่างที่ 1 — เข้าสู่ระบบ (Login)

```
Function: เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน
Actor: ผู้ใช้งานที่ลงทะเบียนแล้วทุกบทบาท
Input: email (string, required, valid email format), password (string, required)
Process:
  1. ตรวจสอบรูปแบบ input
  2. ค้นหาบัญชีผู้ใช้จาก email ผ่าน Auth.js provider
  3. ตรวจสอบรหัสผ่าน (hash compare)
  4. หากถูกต้อง สร้าง session/JWT พร้อม role และ scope ของผู้ใช้
  5. หากผิดเกินจำนวนครั้งที่กำหนด ล็อกบัญชีชั่วคราว
Output: session token (httpOnly cookie) + redirect ไปหน้าตามบทบาท
Permission: Guest เท่านั้นที่เรียกฟังก์ชันนี้ได้ (ผู้ที่ login แล้วถูก redirect ออก)
Validation: email รูปแบบถูกต้อง, password ไม่ว่าง, rate limit ต่อ IP/account
Error State:
  - Invalid credentials → แสดงข้อความทั่วไป "อีเมลหรือรหัสผ่านไม่ถูกต้อง" (ไม่ระบุว่าผิดฝั่งใด)
  - Account locked → แจ้งเวลาที่ต้องรอ
  - Server error → แสดงข้อความทั่วไป, log รายละเอียดฝั่ง server เท่านั้น
Audit: บันทึกทุกครั้งที่ login สำเร็จ/ล้มเหลว พร้อม timestamp, IP, user-agent
Acceptance Criteria:
  - AC1: ผู้ใช้ที่กรอกข้อมูลถูกต้องเข้าสู่ระบบสำเร็จและได้รับ session ที่มี role ถูกต้อง
  - AC2: ผู้ใช้ที่กรอกรหัสผ่านผิด 5 ครั้งติดต่อกันถูกล็อกบัญชีชั่วคราวตามนโยบาย
  - AC3: ไม่มีข้อมูล credential รั่วไหลผ่าน error message หรือ log ที่ไม่ได้ mask
```

### ตัวอย่างที่ 2 — นำเข้ารายชื่อผู้เข้าสอบผ่าน Excel

```
Function: นำเข้ารายชื่อผู้เข้าสอบจากไฟล์ Excel (batch import)
Actor: Registrar Staff, Regional Admin, Central Officer (ตาม scope ของตน)
Input: ไฟล์ .xlsx ตาม template ที่กำหนด (คอลัมน์: เลขทะเบียน, ชื่อ-นามสกุลสมมติ, ระดับชั้น, สนามสอบ, สังกัด)
Process:
  1. ตรวจสอบชนิดไฟล์และขนาดไฟล์
  2. Parse เป็นรายแถว และตรวจสอบ validation รายแถว (dry-run) โดยยังไม่บันทึกลงฐานข้อมูล
  3. แสดงรายงานสรุป: จำนวนแถวถูกต้อง/ผิดพลาด พร้อมระบุแถวและเหตุผลที่ผิดพลาด
  4. ผู้ใช้ยืนยันการนำเข้า → ระบบบันทึกเฉพาะแถวที่ถูกต้องภายใน transaction เดียว (หรือแบ่งชุดที่ rollback ได้อิสระต่อกัน)
  5. หากเกิดข้อผิดพลาดระหว่างบันทึกจริง ให้ rollback ทั้งชุดที่กำลังประมวลผลและแจ้งผู้ใช้
Output: รายงานผลการนำเข้า (สำเร็จ/ล้มเหลว/รายละเอียดต่อแถว) + ไฟล์ error log ให้ดาวน์โหลด
Permission: เฉพาะบทบาทที่ระบุ และเฉพาะสังกัด/เขตที่ผู้ใช้มีสิทธิ์เท่านั้น (ตรวจสอบ scope ทุกแถวฝั่ง server ไม่เชื่อค่าที่ client ส่งมา)
Validation:
  - เลขทะเบียนไม่ซ้ำกับข้อมูลที่มีอยู่ (unless explicitly flagged as update)
  - ระดับชั้น/สนามสอบต้องมีอยู่จริงในข้อมูลอ้างอิง
  - ฟิลด์บังคับต้องไม่ว่าง และรูปแบบข้อมูลถูกต้องตามชนิด
Error State:
  - ไฟล์ผิดรูปแบบ/เสียหาย → ปฏิเสธก่อนเริ่มประมวลผล พร้อมข้อความชัดเจน
  - พบแถวผิดพลาดบางส่วน → ไม่บันทึกแถวที่ผิด, รายงานแยกจากแถวที่ถูกต้อง, ผู้ใช้เลือกได้ว่าจะนำเข้าเฉพาะแถวที่ถูกต้องหรือยกเลิกทั้งหมด
  - ระบบขัดข้องระหว่างบันทึก → rollback อัตโนมัติ, ไม่มีข้อมูลค้างในสถานะไม่สมบูรณ์
Audit: บันทึกผู้ทำรายการ, เวลานำเข้า, ไฟล์ต้นฉบับ (checksum/ชื่อไฟล์), จำนวนแถวที่สำเร็จ/ล้มเหลว
Acceptance Criteria:
  - AC1: ไฟล์ที่มีข้อมูลถูกต้องทั้งหมดนำเข้าสำเร็จ 100% และปรากฏใน M1 ทันที
  - AC2: ไฟล์ที่มีแถวผิดพลาดบางส่วนไม่ทำให้แถวที่ถูกต้องถูกบล็อกไปด้วย (เมื่อผู้ใช้เลือกนำเข้าเฉพาะแถวถูกต้อง)
  - AC3: ผู้ใช้นอก scope ของตน (เช่น พยายามนำเข้าข้อมูลสังกัดอื่น) ถูกปฏิเสธฝั่ง server แม้ request จะถูกแก้ไขจาก client
  - AC4: ทุกการนำเข้ามี audit record ที่สืบย้อนได้ว่าใครนำเข้า ไฟล์ใด เมื่อใด ผลลัพธ์อย่างไร
```

> โมดูลอื่นทั้งหมด (M1–M9) จะจัดทำ full function spec ตาม template นี้เป็นเอกสารย่อยเมื่อเริ่มเฟสพัฒนาโมดูลนั้น (ดูแผนเฟสใน `project-charter.md` ข้อ 12) — การพยายามระบุทุกฟังก์ชันของทั้งระบบไว้ล่วงหน้าในเฟส P0 จะทำให้เอกสารล้าสมัยก่อนเริ่มพัฒนาจริง จึงจำกัดเฉพาะตัวอย่างสาธิตรูปแบบในเอกสารนี้
