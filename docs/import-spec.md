# Excel Import Template — บุคคล + การแต่งตั้งตำแหน่ง (P7 Excel, PDF & Data Operations)

งาน: **"สร้าง Excel Import Template"** — ส่งมอบเฉพาะ **แม่แบบไฟล์ Excel
(`templates/*.xlsx`) และเอกสาร mapping ฉบับนี้** เท่านั้น **ไม่รวม** import
engine/Server Action/หน้า UI จริง (ดู §7 "ขอบเขตที่ตัดออก")

## 1. ขอบเขตงานและการตัดสินใจสำคัญ

### 1.1 เป้าหมายการนำเข้า: Person + Appointment (M7 ทะเบียนบุคลากร) — ไม่ใช่คลังข้อสอบ/ผู้สมัครสอบ

ยืนยันขอบเขตจากเอกสารโครงการหลายฉบับก่อนออกแบบ:

- `prisma/question-bank.md` §6 ระบุชัดเจนว่า Excel Import ผูกกับ **M7
  (ทะเบียนบุคลากร)** ไม่ใช่คลังข้อสอบ
- `prisma/sitemap.md` §4.5/§5.2 กำหนดหน้า `/registry/import` (Registrar
  Staff, ขอบเขตหน่วยงานตนเอง) และ `/admin/import` (Central Officer/
  Super Admin, ข้ามหน่วยงาน) ทั้งคู่จัดอยู่ใต้หมวด M1 ทะเบียน ไม่ใช่ M3/M4
  (คลังข้อสอบ/แบบทดสอบ)
- `prisma/user-flows.md` F6.3 "นำเข้าข้อมูล Excel ระดับศูนย์กลาง" ระบุ Actor
  เป็น Central Officer/Super Admin เช่นกัน
- `prisma/requirements.md` §8 ตัวอย่างที่ 2 อ้างถึงคอลัมน์แบบทะเบียนบุคคล
  (เลขทะเบียน/ชื่อ-นามสกุล ฯลฯ) สอดคล้องกับแนวทางนี้

จึงสรุปว่าแม่แบบนี้ต้องนำเข้า **`Person`** (บุคคล) และ **`Appointment`**
(การแต่งตั้งดำรงตำแหน่งที่หน่วยงาน) ซึ่งเป็นคู่ entity เดียวที่ (ก) มี schema
รองรับสมบูรณ์แล้วจริงตั้งแต่ P2 (`Organization.code`, `Position.code`,
`Person`, `Appointment`) และ (ข) ตรงกับคำอธิบาย "ทะเบียนบุคลากร" ในทุกเอกสาร
ข้างต้น

### 1.2 หนึ่งแถว = หนึ่งการแต่งตั้ง (ไม่แยกชีท Person กับ Appointment)

ออกแบบให้ชีทข้อมูลหลัก ("นำเข้าบุคคลและการแต่งตั้ง") มี 1 แถวต่อ 1 การแต่งตั้ง
1 รายการ (บุคคล 1 คน + ตำแหน่ง 1 ตำแหน่ง + หน่วยงาน 1 แห่ง) แทนที่จะแยกเป็น 2
ชีท (ชีท Person แยกจากชีท Appointment แล้วเชื่อมด้วย key) เพราะ:

- ตรงกับ workflow การใช้งานจริงที่สุด: ผู้ปฏิบัติงานทะเบียนมักมีข้อมูล "แต่งตั้ง
  ใครคนหนึ่งไปดำรงตำแหน่งใด" มาเป็นชุดเดียวกันอยู่แล้ว (เช่น จากมติที่ประชุม/
  ประกาศแต่งตั้ง 1 ฉบับ)
- ลดความซับซ้อนของ two-pass import (สร้าง Person ก่อน แล้วจึงสร้าง
  Appointment อ้างอิง key ที่เพิ่งสร้าง) ซึ่งเป็นงานของ import engine ในอนาคต
  ไม่ใช่ขอบเขตของงาน template ฉบับนี้
- คอลัมน์ `รหัสอ้างอิงบุคคล` (referenceCode) ยังทำหน้าที่เป็น "natural key"
  ให้คนคนเดียวกันแต่งตั้งหลายตำแหน่ง/หลายแถวได้ (กรอกซ้ำ referenceCode เดิม)
  โดยไม่ต้องสร้างบุคคลซ้ำ (ดู §1.3)

**ข้อจำกัดที่ยอมรับจากการตัดสินใจนี้**: ถ้าผู้ใช้ต้องการนำเข้า "บุคคลเฉยๆ
โดยยังไม่มีตำแหน่ง" ไม่สามารถทำได้ด้วยแม่แบบนี้ (ทุกแถวต้องมีการแต่งตั้งเสมอ)
— บันทึกเป็นขอบเขตที่ตัดออก (§7)

### 1.3 กติกาจับคู่/สร้างบุคคลใหม่ด้วย `referenceCode`

ออกแบบ (สำหรับ import engine ในอนาคตนำไปใช้จริง — งานนี้ยังไม่ implement):

| กรณี | พฤติกรรมที่ออกแบบไว้ |
|---|---|
| มี `referenceCode` และตรงกับ `Person.referenceCode` ที่มีอยู่แล้ว | จับคู่บุคคลเดิม — ถ้า `prefix`/`fullName` ในแถวต่างจากข้อมูลเดิม ต้อง**แจ้งเตือนผู้ใช้ก่อนเขียนทับ** (ไม่ silent-overwrite) เพราะอาจเป็นการพิมพ์ชื่อผิดโดยไม่ตั้งใจ |
| มี `referenceCode` แต่ไม่พบในระบบ | สร้าง `Person` ใหม่ด้วย `referenceCode` นั้น |
| ไม่มี `referenceCode` (เว้นว่าง) | สร้าง `Person` ใหม่เสมอ (ไม่พยายาม dedupe ด้วยชื่อ เพราะชื่อซ้ำกันได้จริงในทางปฏิบัติ — ไม่ปลอดภัยที่จะเดา) |

### 1.4 ข้อจำกัดที่รับไว้อย่างตรงไปตรงมา: `Organization.code` ไม่บังคับทุกหน่วยงาน

`Organization.code` เป็น `String?` (nullable, partial-unique — ดู
`prisma/data-dictionary.md`) ไม่ใช่ทุกหน่วยงานในระบบจะมีรหัส เนื่องจากแม่แบบนี้
ใช้ `Organization.code` เป็น **lookup key เดียว** สำหรับคอลัมน์
"รหัสหน่วยงาน..." (เพื่อให้เป็นข้อความสั้น พิมพ์ง่าย กว่าการใช้ `id` แบบ cuid)
**หน่วยงานที่ยังไม่มีรหัสจะไม่สามารถเป็นเป้าหมายของการนำเข้าด้วยแม่แบบนี้ได้**
จนกว่าจะมีการกำหนดรหัสให้ก่อน (ผ่านหน้า `/admin/registry/[id]` ที่มีอยู่แล้ว) —
บันทึกเป็นงานถัดไป (§8) ไม่ใช่บั๊กของแม่แบบ

`Position.code` ไม่มีปัญหานี้ (เป็น `String` **NOT NULL** + `@unique` เสมอ)

### 1.5 เวอร์ชันของแม่แบบ

กำหนด **Template Version 1.0.0** (semantic-ish: MAJOR = โครงสร้างคอลัมน์
เปลี่ยนแบบ breaking, MINOR = เพิ่มคอลัมน์/ชีทอ้างอิงใหม่แบบไม่ breaking, PATCH =
แก้ข้อความ/รายการอ้างอิง) บันทึกไว้เป็น cell ข้อความในชีท "คำแนะนำ" (ไม่ใส่ใน
ชื่อไฟล์ เพื่อไม่ให้ลิงก์ดาวน์โหลดเปลี่ยนทุกครั้งที่ minor bump) — ค่าคงที่
`TEMPLATE_VERSION` ประกาศอยู่ที่ต้นไฟล์ `scripts/generate-import-template.mjs`
เป็น single source of truth

### 1.6 เครื่องมือสร้างไฟล์: `exceljs`

"วิธีตรวจสอบ" ของบรีฟระบุ **"template มี validation"** ซึ่งหมายถึง Excel
data-validation จริงในไฟล์ (dropdown/date constraint) ไม่ใช่แค่คำอธิบายใน
เอกสาร — ไลบรารีเดียวในระบบนิเวศ Node.js ที่เขียน `<dataValidation>` XML ของ
OOXML ได้ครบและยัง maintain อยู่คือ [`exceljs`](https://www.npmjs.com/package/exceljs)
(เวอร์ชัน 4.4.0 ณ วันที่ทำงานนี้) ติดตั้งจริงด้วย `npm install exceljs` (ยืนยัน
เครือข่ายใช้งานได้ในสภาพแวดล้อมนี้) เพิ่มเข้า `dependencies` (ไม่ใช่
`devDependencies`) ในเจตนาว่า import engine ในอนาคต (Server Action ที่ต้อง
**อ่าน** ไฟล์ .xlsx ที่ผู้ใช้อัปโหลด) จะต้องใช้ไลบรารีเดียวกันนี้ที่ runtime ด้วย

### 1.7 หนึ่งไฟล์ 5 ชีท แทนที่จะแยกหลายไฟล์

`ผลลัพธ์ที่ต้องส่ง` ของบรีฟระบุ `templates/*.xlsx` (glob) — ตีความว่าเป็น
โฟลเดอร์ปลายทาง ไม่ใช่ข้อบังคับว่าต้องมีหลายไฟล์จริง เลือกทำ **ไฟล์เดียว
`templates/person-appointment-import-template.xlsx` ที่มี 5 ชีท** แทนการแยก
หลายไฟล์ เพราะ Excel data-validation แบบ list ที่อ้างอิงชีทอื่น
(`formulae: ["'รหัสหน่วยงานอ้างอิง'!$A$2:$A$11"]`) ทำงานได้น่าเชื่อถือเฉพาะเมื่อ
ชีทต้นทางอยู่ใน **workbook เดียวกัน** เท่านั้น (external workbook reference
ใช้งานได้ไม่แน่นอนข้าม Excel/LibreOffice/Google Sheets) การรวมไฟล์เดียวยังทำให้
แจกจ่าย/เก็บเวอร์ชันง่ายกว่าด้วย

รายชื่อ 5 ชีท: `คำแนะนำ`, `รหัสหน่วยงานอ้างอิง`, `รหัสตำแหน่งอ้างอิง`,
`ค่าที่อนุญาต`, `นำเข้าบุคคลและการแต่งตั้ง` (ชีทข้อมูลหลัก)

### 2.1 ชีทอ้างอิง (dropdown source)

- **`รหัสหน่วยงานอ้างอิง`** — คอลัมน์ A `Organization.code`, B ประเภทหน่วยงาน,
  C ชื่อหน่วยงาน — คัดลอกจาก `prisma/seed.ts` (`seedOrganizations`) ตรงๆ 10
  รายการ (ข้อมูลจำลองทั้งหมด มี "(ข้อมูลจำลอง)" กำกับทุกชื่อ)
- **`รหัสตำแหน่งอ้างอิง`** — คอลัมน์ A `Position.code`, B ชื่อตำแหน่ง, C
  ประเภทหน่วยงานที่เหมาะสม (advisory), D ดำรงได้คนเดียวหรือไม่ — คัดลอกจาก
  `prisma/seed.ts` (`seedPositions`) ตรงๆ 8 รายการ **ไม่รวม** ตำแหน่งทดสอบที่
  Playwright suite อื่นสร้างค้างไว้ในฐานข้อมูล dev จริง (เช่น `E2E_TEST_POS`
  ที่พบระหว่างตรวจสอบฐานข้อมูลสด — ดู §5) เพราะรายการนี้อ้างอิงจาก seed.ts
  โดยตรง ไม่ได้ query จากฐานข้อมูลสด
- **`ค่าที่อนุญาต`** — คอลัมน์ A ค่า enum `AppointmentStatus` ทั้ง 6 ค่า
  (`ACTIVE`/`RESIGNED`/`REMOVED`/`TRANSFERRED`/`DECEASED`/`EXPIRED`), คอลัมน์ B
  คำอธิบายภาษาไทย

**คำเตือนสำคัญที่ระบุไว้ในชีท "คำแนะนำ" ของไฟล์ด้วย**: รหัสในชีทอ้างอิงเหล่านี้
เป็น **ข้อมูลจำลองที่ตรงกับชุด seed ของสภาพแวดล้อม dev/test เท่านั้น** เมื่อ
นำไปใช้งานจริง ต้องแทนที่ด้วยรหัสหน่วยงาน/ตำแหน่งจริงจากฐานข้อมูล Production
(และห้ามใช้ก่อนผ่าน Real-data Readiness Gate ตามข้อจำกัดมาตรฐานของโครงการ)

## 3. Function Specification — `importPersonAppointmentBatch()` (แนวคิด, ยังไม่ implement)

บรีฟกำหนดให้ "ทุกฟังก์ชันต้องระบุ Actor, Input, Process, Output, Permission,
Validation, Error State, Audit, Acceptance Criteria" — งานนี้ **ไม่ได้สร้าง
ฟังก์ชันนี้จริง** (ขอบเขตงานคือ template + spec เท่านั้น) แต่ระบุ spec ไว้ที่นี่
เพื่อเป็นข้อกำหนดให้งานถัดไปที่จะ implement import engine จริงนำไปใช้ต่อได้
โดยไม่ต้องออกแบบใหม่ตั้งแต่ต้น

| หัวข้อ | รายละเอียด |
|---|---|
| **Actor** | SUPER_ADMIN, CENTRAL_OFFICER (คู่ M7 ตาม `roles-permissions.md` §3 — `Execute(ALL)`); REGIONAL_ADMIN, REGISTRAR_STAFF (`Execute(OWN_ORG_SUBTREE)` — ต้องตรวจว่าทุกแถวที่นำเข้าอยู่ในขอบเขตหน่วยงานตนเองเท่านั้น) |
| **Input** | ไฟล์ `.xlsx` ที่สร้างจากแม่แบบนี้ (หรือมีโครงสร้างคอลัมน์ตรงกัน) อัปโหลดผ่าน `/registry/import` หรือ `/admin/import` (ดู `sitemap.md`) |
| **Process** | (1) parse ไฟล์ด้วย `exceljs` อ่านเฉพาะชีท "นำเข้าบุคคลและการแต่งตั้ง" ตั้งแต่แถวที่ 3 เป็นต้นไป (2) validate ทีละแถวแบบ **dry-run ไม่เขียนฐานข้อมูล** — สร้างรายงานผล (แถวไหนผ่าน/ไม่ผ่าน พร้อมเหตุผล) ตาม `requirements.md` §8 ตัวอย่างที่ 2 (3) ให้ผู้ใช้ยืนยัน (confirm) หลังเห็นรายงาน (4) เขียนเฉพาะแถวที่ผ่าน validation ภายใน transaction เดียวหรือแบ่งเป็น batch ที่ rollback อิสระต่อกันได้ (5) สำหรับแต่ละแถว: lookup/สร้าง `Person` ตามกติกา §1.3 → `SELECT ... FOR UPDATE` ล็อกแถว `positions` แล้วตรวจ `isUniquePerOrganization` แบบเดียวกับ `createAppointment()` ที่มีอยู่แล้วใน `src/lib/admin-registry-mutations.ts` (ดู `admin-organization.md` §2.6) ก่อน INSERT `Appointment` ใหม่ (6) idempotent/retry-safe ตาม `architecture.md` §9.1 — ต้องไม่สร้างข้อมูลซ้ำถ้า retry งานเดิม |
| **Output** | รายงานผลนำเข้า: จำนวนแถวสำเร็จ/ล้มเหลว, รายชื่อ `Person`/`Appointment` ที่สร้าง/จับคู่ พร้อม id จริง |
| **Permission** | ตรวจฝั่ง server ผ่าน `requirePermission("REGISTRY", "create", {organizationId})` **ทุกแถว** (แถวที่อยู่นอกขอบเขต scope ของผู้ใช้ต้องถูกปฏิเสธเป็นรายแถว ไม่ใช่ปฏิเสธทั้งไฟล์ — ยกเว้น SUPER_ADMIN/CENTRAL_OFFICER ที่ scope=ALL) — deny-by-default |
| **Validation** | ต้องตรวจซ้ำทุกกติกาที่ dropdown/date-validation ของ Excel ตรวจไม่ได้: (ก) `organizationCode`/`positionCode` มีอยู่จริงและยังไม่ถูก soft-delete/`isActive=false` ณ เวลานำเข้าจริง (ข) `isUniquePerOrganization` ไม่ชนกับการแต่งตั้งที่ยัง ACTIVE อยู่ (ค) `endDate` > `startDate` ถ้าระบุทั้งคู่ (ง) unique constraint `(organizationId, positionId, personId, startDate)` ไม่ซ้ำ (จ) `referenceCode` ซ้ำกันภายในไฟล์เดียวกันต้องจับคู่เป็นบุคคลเดียวกันทุกแถว (ไม่ใช่คนละคน) |
| **Error State** | แถวที่ validate ไม่ผ่าน → ไม่เขียนฐานข้อมูล รายงานเป็นข้อความไทยชี้เฉพาะแถว/คอลัมน์ที่ผิด — ถ้า DB connection ขาดระหว่างเขียน batch ใดๆ → `withTransaction()` rollback batch นั้น (รูปแบบเดียวกับ `admin-registry-mutations.ts`) แถวที่เขียนสำเร็จไปแล้วใน batch ก่อนหน้าไม่ถูกย้อนกลับ (per-batch atomicity ไม่ใช่ all-or-nothing ทั้งไฟล์ เพื่อไม่ให้ไฟล์ใหญ่ล้มเหลวทั้งหมดจาก 1 แถวผิด) |
| **Audit** | ทุก `Person`/`Appointment` ที่สร้าง/จับคู่จากการนำเข้อต้องเขียน `audit_logs` ระบุ `entityType`, `action` (`CREATE`/`MATCH`), ผู้ทำรายการ, และ **เลขอ้างอิงงานนำเข้า (import batch id)** เพื่อสืบย้อนได้ว่าแถวไหนมาจากไฟล์ import ชุดใด — ไม่ overwrite ประวัติเดิม (Appointment ปิดวาระ = UPDATE แถวเดิมเท่านั้น ตาม `data-policy.md` ข้อ 7) |
| **Acceptance Criteria** | นำเข้าไฟล์ตัวอย่าง (แถวตัวอย่าง 3 แถวในแม่แบบนี้) แล้วได้ `Person`/`Appointment` ตรงตามที่คาด, แถวที่จงใจใส่รหัสหน่วยงาน/ตำแหน่งผิดถูกปฏิเสธพร้อมข้อความชี้จุดผิด, แถวที่ referenceCode ซ้ำกับบุคคลเดิมไม่สร้างบุคคลซ้ำ, แถวที่ละเมิด `isUniquePerOrganization` ถูกปฏิเสธเหมือนกับที่ UI `/admin/registry/appointments` ปฏิเสธ |

## 6. ความเสี่ยง/ข้อจำกัด

- **Excel dropdown ไม่ใช่การป้องกันที่สมบูรณ์** — ผู้ใช้ paste ค่านอกรายการเข้า
  เซลล์ได้โดย Excel ไม่บล็อก (บล็อกเฉพาะการพิมพ์ตรงๆ) import engine ในอนาคต
  ต้อง validate ซ้ำที่ server เสมอ (ระบุไว้ชัดเจนใน §3/§4)
- **ชีทอ้างอิงเป็นภาพนิ่ง ณ เวลาที่สร้างไฟล์** — ถ้าหน่วยงาน/ตำแหน่งในระบบจริง
  เปลี่ยนแปลงหลังแจกจ่ายไฟล์ไปแล้ว ผู้ใช้อาจเห็นรหัสที่ไม่ตรงกับปัจจุบัน (ดู §4)
- **ยังไม่มี import engine จริงผูกอยู่** — แม่แบบนี้และเอกสารนี้เป็นเพียงจุด
  เริ่มต้นสำหรับงานถัดไป (§8) ไม่สามารถใช้นำเข้าข้อมูลได้จริงในตอนนี้
- **`Organization.code` ไม่บังคับ** อาจทำให้หน่วยงานบางแห่งไม่สามารถเป็นเป้าหมาย
  นำเข้าได้จนกว่าจะกำหนดรหัส (§1.4) — ไม่ใช่บั๊ก แต่เป็นข้อจำกัดที่สืบทอดมาจาก
  การออกแบบ schema ตั้งแต่ P2
- **ข้อมูลอ้างอิงในไฟล์เป็นข้อมูลจำลองล้วน (ตรงกับ seed.ts)** — ห้ามใช้แม่แบบ
  ฉบับนี้ (พร้อมชีทอ้างอิงชุดนี้) กับข้อมูลจริงโดยตรง ต้องสร้างชีทอ้างอิงใหม่จาก
  ข้อมูล Production จริงก่อนเสมอ

## 7. ขอบเขตที่ตัดออก (โปร่งใส สำหรับ Owner Review)

- **Import engine/Server Action/UI จริง** — ไม่ได้สร้างในงานนี้ตามที่บรีฟกำหนด
  ขอบเขตไว้ชัดเจน (`ผลลัพธ์ที่ต้องส่ง: templates/*.xlsx, import-spec.md`
  เท่านั้น) — §3 เป็นเพียง spec เตรียมไว้ให้งานถัดไป
- **หน้า `/registry/import` และ `/admin/import` ตาม `sitemap.md`** — ยังไม่ถูก
  สร้าง เป็นงานอนาคตที่ต้องใช้ spec ใน §3 เป็นจุดเริ่มต้น
- **ไม่รองรับนำเข้าบุคคลที่ยังไม่มีตำแหน่ง** (§1.2) — ทุกแถวต้องมีการแต่งตั้ง
  เสมอในแม่แบบนี้ ถ้าต้องการนำเข้า "บุคคลเฉยๆ" ต้องออกแบบชีท/แม่แบบแยกในงานถัดไป
- **ไม่รองรับนำเข้าหน่วยงาน (`Organization`) หรือตำแหน่ง (`Position`) ใหม่ผ่าน
  Excel** — สมมติว่าหน่วยงาน/ตำแหน่งเป้าหมายมีอยู่แล้วในระบบผ่านหน้า
  `/admin/registry/*` ที่มีอยู่แล้ว (ตาม `admin-organization.md`) แม่แบบนี้ใช้
  เพียง**อ้างอิง**หน่วยงาน/ตำแหน่งที่มีอยู่แล้วเท่านั้น
- **ไม่มีกลไก auto-update ชีทอ้างอิงจากฐานข้อมูลสด** — ต้องรัน
  `node scripts/generate-import-template.mjs` ใหม่ด้วยมือทุกครั้งที่ต้องการ
  ปรับรายการอ้างอิงให้ตรงกับข้อมูลจริง (§4)
- **ไม่รองรับหลายภาษา** — แม่แบบเป็นภาษาไทยเท่านั้น (ตรงกับ UI ทั้งหมดของระบบ
  ณ ปัจจุบัน)

## 8. งานถัดไปที่ควรทำ

1. Implement import engine จริงตาม spec ใน §3 — เป็น System Job ตาม
   `architecture.md` §9.1 (อ่านไฟล์จาก Object Storage, validate ทีละแถวใน
   transaction, idempotent/retry-safe, ไม่ทิ้งสถานะครึ่งๆ กลางๆ เมื่อล้มเหลว)
2. สร้างหน้า `/registry/import` (Registrar Staff, ขอบเขตหน่วยงานตนเอง) และ
   `/admin/import` (Central Officer/Super Admin, ข้ามหน่วยงาน) ตาม
   `sitemap.md` §4.5/§5.2 พร้อม dry-run preview/รายงานผลก่อนยืนยันเขียนจริง
   ตาม `requirements.md` §8 ตัวอย่างที่ 2
3. บันทึก audit log พร้อม "import batch id" ที่สืบย้อนได้ (§3 คอลัมน์ Audit) —
   ต้องออกแบบว่าจะเก็บ batch id ไว้ที่ตารางใด (อาจต้องเพิ่มตารางใหม่
   `import_jobs` หรือ `import_batches`)
4. พิจารณาบังคับให้ `Organization.code` เป็นค่าที่ต้องมีก่อนเข้าสู่ขั้นตอนแต่งตั้ง
   ผ่านการนำเข้า Excel (ทางเลือก: บังคับที่ UI `/admin/registry` ให้ต้องกรอก
   code ก่อนบันทึก หรือคงเป็น nullable แต่กรองหน่วยงานที่ไม่มี code ออกจาก
   dropdown การนำเข้าโดยอัตโนมัติ)
5. เมื่อ import engine เสร็จ ให้เพิ่มสคริปต์ที่ query รหัสหน่วยงาน/ตำแหน่งจาก
   ฐานข้อมูล Production จริง (กรองเฉพาะ `isActive=true`/`status=ACTIVE`) มา
   generate ชีทอ้างอิงของแม่แบบโดยอัตโนมัติ แทนการ hardcode ค่าจาก seed.ts
   เหมือนงานนี้ (ซึ่งเหมาะเฉพาะสภาพแวดล้อม dev/test เท่านั้น)
6. ออกแบบและ implement ชีท/แม่แบบแยกสำหรับ "นำเข้าบุคคลเฉยๆ โดยยังไม่มีตำแหน่ง"
   ถ้ามี use case จริงที่ต้องการ (ต่อยอดจาก §7)
